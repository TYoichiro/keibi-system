# 警備員管理システム 試験運用の準備票

作成日: 2026年10月8日（日本時間）

状態: 新しい提案・記入用の草案。運用担当、数値、手順は確認前

この資料は、[初回要件書](MVP_REQUIREMENTS.md)のQ08（変更連絡）、Q09（アカウント運用）、Q10（訂正・保存・削除）と、試験運用の担当・規模を具体化するための準備票。既存の[セキュリティチェックリスト](../SECURITY_CHECKLIST.md)を繰り返すのではなく、誰が、いつ、どの手順を使い、何を証跡として残すかを記入する。

今回行うのは資料の準備まで。アプリ、DB、認証、外部サービス、本番環境は変更しない。以下の提案を記入しただけで要件の承認・試験運用開始・安全性の確認が済んだ扱いにしない。空欄は未決を表す。承認した内容は要件書・データ設計・実装依頼に反映する。

パスワード、復旧コード、秘密鍵、本人確認書類、実在する隊員の個人情報はこの資料やGitへ記入しない。連絡先や運用証跡の実体はアクセス制限した保管場所で管理し、この資料には担当の役割と参照先を記載する。

## 2 アカウント発行と復旧（Q09）

本人用メールを利用できることは確認済みだが、認証基盤・配信手段・有効化と復旧の詳細は未決。Better Authは候補であり採用決定ではない。費用・契約・保存地域の確認を含め、選定結果はデータ設計に反映する。

候補の公式資料を2026年10月8日に確認した。以下の最小8文字・scrypt・再設定時の他セッション非失効は、その時点の候補の既定値であり、このシステムが採用する値ではない。採用時には固定するバージョンの公式仕様を再確認する。[Better Auth: Email & Password](https://better-auth.com/docs/authentication/email-password)、[Better Auth: 多要素認証](https://better-auth.com/docs/plugins/2fa)

| 統合する事項 | 候補と既存基準の差分・必要条件 | 着手前に残す設計・検証計画の証跡 |
| --- | --- | --- |
| パスワード長 | 候補の既定は最小8・最大128。既存ヘルパーは15〜128 | 採用バージョンと長さの設定。登録・変更・再設定の全経路で14/15/128/129文字、空白・Unicodeの扱いを確認するケース |
| ハッシュ | 候補の既定はscrypt。既存方針はArgon2id | 既存ヘルパーを接続するアダプター仕様と、作成・変更・再設定後のハッシュ保存/照合を確かめるケース。平文・トークンを証跡へ保存しない |
| セッション失効 | 候補は再設定時に他セッションを既定で失効しない。既存基準では停止・退職・権限縮小後の旧権限を許可しない | 再設定後の全セッション失効を含む採用案、停止と権限更新の判定経路。古いCookieで次の取得・更新を拒否するケース |
| 公開登録の停止 | メール認証機能を有効にするだけでは会社管理者による発行限定にならない | 公開登録を止める設定・ルート一覧、管理者発行から所属確定までの手順。直接登録でアカウント・所属・管理者権限を得られないケース |
| メール有効化 | 候補は配信処理とメール確認必須の設定を別に必要とする | 送信処理、有効化前の許可範囲、期限・一度限り・旧案内失効の設計。未確認・不達・期限切れのまま業務APIへ入れないケース |
| 会社管理者のMFA | 候補にTOTP等の機能があっても、会社管理者への必須適用は別に設計する | 登録・確認済み状態と業務APIの拒否条件、昇格・復旧時の扱い。MFA未完了や解除後の直接API操作を拒否するケース |
| Origin等の既存対策 | 認証基盤の組込み後もOrigin・CSRF・本文上限・試行制限を維持する | ミドルウェア順序、許可Origin、Cookie、例外経路と理由。許可外送信元、巨大本文、連続認証、ログへの秘密混入を確認するケース |

ここで求める着手前の証跡は採用設定と確認ケースの設計記録。実装後は選定したバージョンの実際のAPI経路で結果を記録し、設計しただけのケースを合格扱いにしない。

## 3 配置変更の連絡と障害時の業務（Q08）

初回は自動通知・既読を実装対象にしない。システムの予定反映と本人に伝わったことを分け、既存の連絡手段で次を記録できる運用を決める。これは初回に新しい通知・既読機能を追加する提案ではない。

| 記入する事項 | 決定内容 |
| --- | --- |
| 確定・改訂・取消の連絡担当と代行 |  |
| 使用する連絡手段・安全に伝える項目 |  |
| 本人と取引先への連絡が必要になる条件 |  |
| 連絡期限、連絡がつかない場合の再連絡と代替担当 |  |
| 連絡結果の保管場所と、緊急変更の承認方法 |  |
| 勤務開始後・終了後の訂正の承認担当（Q10） |  |

連絡記録の項目案: 勤務枠の参照、変更前後の日時・担当、変更理由、変更判断者、連絡者・時刻、相手、連絡結果、未達時の次の対応。鍵や暗証番号等は通常の連絡本文に含めず、扱う場合はQ07の公開範囲と専用の取扱手順を確認する。

障害中から復旧までの手順案は次のとおり。担当・保管場所・開始条件を記入し、実データ利用前に試す。

1. 障害を受け付け、利用可能な範囲と最後に確認できた予定の時刻を整理する。保存中の操作は成功・失敗を推測せず、確認待ちとして区別する。
2. 利用会社の担当が代替の配置台帳と連絡手段へ切り替える。障害中に確定した変更と、調整中の案を分ける。台帳の参照先: ______。
3. 障害中の記録には、勤務枠・日時・隊員、変更理由・判断者・時刻、本人等への連絡結果を残す。勤怠実績は既存の記録方法で別に扱う。
4. 復旧した環境を一般利用へ戻す前に、復元時点後の利用停止・退職・権限縮小・メール変更・削除を確認し、古い権限や認証状態が戻らないよう反映する。旧セッションを再利用できるかも検証する。
5. 利用会社の会社管理者が、保存成否不明の操作、障害中の変更、復元後の予定を照合する。重複確定、古い予定の再公開、取消の取り消しを防ぎ、必要な訂正は履歴と理由を残して反映する。
6. 最新の勤務予定と本人への連絡結果を照合し、未解決分・責任者・対応期限を記録する。再開判断者が確認して利用者へ案内する。
