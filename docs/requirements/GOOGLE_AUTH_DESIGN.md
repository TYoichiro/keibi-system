# Googleログインの設計・実装条件

更新日: 2026年10月8日（日本時間）

ユーザーの指定により、全利用者のログイン方式をGoogleログイン（OAuth 2.0 + OpenID Connect / OIDC）に確定した。本資料はその方針と今後の実装条件をまとめる。現在は画面モックのみで、Google連携・認証API・利用者テーブル・セッション・認可は未実装。

## 1. 確定した方針と責任分担

管理者・管制担当・閲覧者・警備員が、それぞれ本人のGoogleアカウントでログインする。自システム専用のログインID・パスワードを発行せず、Googleのパスワードを入力・保存・検証するフォームやAPIも作らない。メールとパスワードによる代替ログインは設けない。

| 項目 | 管理する場所 |
| --- | --- |
| Googleアカウントの本人認証、パスワード、二段階認証、パスキー、復旧 | Google。利用者または所属組織のGoogle Workspace管理者が管理 |
| 内部利用者ID、会社・拠点・役割、対応する隊員、利用許可・停止 | 本システム。会社管理者が利用者の所属と権限を管理 |
| Googleアカウントと内部利用者の関連付け | 本システム。検証済みのGoogle識別子と利用開始の確認記録を保持 |
| 本システムへのログイン状態とログアウト、停止後の失効 | 本システム。Googleのログイン状態とは別のセッションを管理 |
| OAuthクライアントの秘密、DB用認証情報 | 本システムのサーバー・秘密管理基盤。フロントエンドやGitへ出さない |

保持しないのは利用者の認証用パスワード・ハッシュ、TOTP秘密、Googleの復旧コード。業務の認可と履歴に必要な内部利用者IDやGoogle識別子は保持する。Googleログインを採用しても、会社境界・権限・セッション・秘密情報の管理は必要である。

2026年10月8日のユーザー回答で、次の運用方針も確定した。

| 項目 | 確定した方針 |
| --- | --- |
| 利用できるGoogleアカウント | 個人のGmailと会社のGoogle Workspace。外部メールで作成した、GmailでもWorkspaceでもないGoogleアカウントは初回の対象外 |
| Google側の二段階認証 | 会社管理者は必須。管制担当・閲覧者・警備員は推奨。必須条件の技術的な確認・強制方法は引き続き検証が必要 |
| アプリセッション | 全役割共通で、本人の操作なし24時間、ログインから最長1か月。先に到達した期限で失効し、自動更新で延長しない |
| 利用者の招待 | 会社管理者が登録した本人のGoogleメール宛てにリンクを送る。発行から7日間有効で、一度限り。再招待時は古いリンクを無効にする |
| Google関連付け変更の承認 | 会社管理者が本人確認の上で承認。会社管理者自身の変更は別の会社管理者が承認し、ほかにいなければ運営者が承認 |
| 最初の会社管理者・全管理者の利用不能 | サービス提供側の運営者が会社・本人を確認し、最初の登録と、全管理者がログインできなくなった際の復旧・管理者交代を行う |

## 2. 利用者の招待と初回の関連付け

1. 会社管理者が本人を確認し、招待先メール、会社・所属拠点、1つの役割、警備員の場合の隊員対応を事前登録する。Googleアカウントそのものを発行する操作ではない。
2. サーバーが暗号学的に安全な推測不能乱数で、発行から7日間有効な一度限りの招待を作成し、会社管理者が登録した本人のGoogleメール宛てにリンクを送る。生の招待トークンをDB・ログに残さず、ハッシュを保存する。再招待時は旧リンクを無効にする。期限到達後の利用と旧リンクの再使用を拒否する。
3. 本人が招待を開いてGoogleで認証する。招待は認証トランザクションとサーバー側で関連付け、会社ID・役割・隊員IDをURLから信用しない。
4. サーバーがIDトークン、招待の期限・未使用・対象メール・所属の有効性を確認する。招待対象メールは検証済みのGoogleメールと照合し、`email_verified`が真でない場合は関連付けしない。検証済みトークンのメールがGmailであるか、Google Workspaceを示す有効な`hd`があることも確認する。GmailでもWorkspaceでもない外部メールのGoogleアカウントは対象外として拒否し、追加本人確認で初回の許可範囲を広げない。Workspaceの会社との対応も招待・本人確認で確かめ、`hd`だけで所属や権限を付与しない。[Googleのメール所有権の説明](https://developers.google.com/identity/sign-in/web/backend-auth)
5. 正規化した`issuer`と`sub`を内部利用者へ一度だけ関連付け、招待の消費と利用者有効化を同一トランザクションで行う。同時利用・二重関連付けはDB制約でも拒否する。

未招待のGoogleアカウントは自動登録しない。メールのドメイン・会社コード・Google認証成功だけで会社への所属や権限を付与しない。最初の会社管理者は運営者が会社と本人を確認する限定した初期設定手順で登録し、一般公開の自己登録にはしない。全会社管理者がログインできなくなった際も、運営者が会社・本人を確認して復旧・管理者交代を行う。具体的な本人確認資料・記録・連絡手順は試験運用前に定める。

初回は1利用者につき1社・1所属拠点・1役割とし、Google識別子を複数の利用者へ重複関連付けしない。会社間の移籍・アカウントの付け替えは本人確認・承認・監査の対象とし、本人のメール入力だけで変更しない。Google関連付け変更の承認は会社管理者が行う。会社管理者自身の変更は別の会社管理者が承認し、ほかにいなければ運営者が承認する。

## 3. 識別子と保存項目

| 保存対象 | 内容・制約 |
| --- | --- |
| 内部利用者 | 内部ID、会社・拠点・役割、隊員対応、招待待ち／有効／停止の状態、権限改訂番号 |
| Google関連付け | provider=`google`、検証後の正規化issuer=`https://accounts.google.com`、`sub`、関連付け日時。`(issuer, sub)`と内部利用者への関連付けを一意にする |
| メール | 招待対象メールと現在のGoogleメールを区別。業務連絡先とは別。表示・案内・初回確認用で、ログイン識別子や認可の根拠にはしない |
| 招待 | 対象利用者、トークンのハッシュ、発行日時、発行から7日後の有効期限、消費日時、発行者。再発行時は旧招待を無効にする |
| アプリセッション | 乱数セッションIDのハッシュ、内部利用者ID、権限改訂番号、作成・最終操作・絶対期限・失効日時 |
| 監査 | 招待・関連付け・変更・停止・認証結果・失効の操作者、対象、理由、時刻、結果。生トークンや認証コードは含めない |

Googleの`email`は変更されることがあるため、通常ログインは必ず`issuer + sub`で既存の関連付けを探す。既知の`sub`でメールが変わっても別利用者にしない。同じメールを持つ別の`sub`を既存利用者へ自動関連付けしない。Googleの氏名・プロフィールから業務上の氏名・隊員対応・所属・役割を上書きしない。[Google OIDCの識別子仕様](https://developers.google.com/identity/openid-connect/openid-connect)

## 4. サーバー側のログイン処理案

Reactはログイン開始と結果表示を担当し、Honoを認証の窓口にする。Authorization Code Flow + PKCE（`S256`）、`state`、`nonce`を使う設計案とする。初回のscopeは`openid email`に限定し、業務用の氏名は既存の利用者情報を使う。Drive・Gmail・Calendar等のAPI権限、`profile`、offline access／refresh tokenは要求しない。

1. サーバーが推測できない`state`・`nonce`・PKCE verifierを生成し、短期・一度限りの認証トランザクションとして開始ブラウザに結び付ける。復帰先は許可したアプリ内パスに限定する。
2. Googleへトップレベルの画面遷移を行う。Google認証画面をアプリ内に再現してパスワードを受け取らない。
3. 登録済みの固定callbackへ戻ったら、ブラウザとの対応、`state`、有効期限、未使用状態を検証する。拒否・取消・コードなし・再送は安全に終了し、新しいセッションを作らない。
4. サーバーだけがGoogleとHTTPSで認証コードを交換する。信頼するDiscovery/JWKSの取得先はGoogleに固定し、IDトークンの署名・許可アルゴリズム・`iss`・`aud`・`exp`・`iat`・`nonce`・`sub`を検証する。必要な場合は`azp`も検証し、署名未検証のJWT復号だけでは受け入れない。
5. 毎回、許可されたGoogleアカウントの範囲と関連付け済み利用者または有効な招待を確認し、停止・無効所属・会社境界違反を拒否する。会社・拠点・役割はDBから確定する。会社管理者の二段階認証必須条件も、実装前に確定する検証方法と確認不能時の方針に従って確認する。
6. 認証トランザクションを消費し、識別子を更新した本システム用セッションを作る。GoogleのID/access tokenは業務API用の認証情報としてブラウザへ渡さず、処理後は保持しない。

Googleの[Discovery情報](https://accounts.google.com/.well-known/openid-configuration)は`S256`対応を公開している。実装時は採用ライブラリでPKCE・トークン検証・エラー・公開鍵更新を確認し、独自の暗号処理を作らない。[OAuthのセキュリティ指針 RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700)

## 5. セッション・CSRF・失効

本番は同一オリジン配信を基本とし、アプリセッションを`HttpOnly`・`Secure`・`SameSite=Lax`、ホスト限定・最小限のPathを持つCookieで管理する。`Lax`はGoogleからのトップレベルGET callbackへの復帰を想定した案。Cookieだけに依存せず、既存Origin・HonoのCSRF対策を維持し、セッションに対応する更新操作のCSRFトークン検証を追加する。トークンの取得方法と送信ヘッダーはAPI契約の実装前に具体化する。

Googleから戻る専用GET callbackは外部からの画面遷移で、通常の更新APIと同じOriginを要求できない。実装時はこのルートだけを明示的に扱い、開始ブラウザに結び付けた`state`・nonce・PKCE・期限・一度限りの検証を適用する。OriginやCSRFを全APIで緩めない。ログイン開始も許可した同一オリジン経路と開始意図を確認し、外部サイトからの意図しない関連付けを防ぐ。

認証コード・招待・`state`を含むcallback URLはAPIだけでなくプロキシ・監視のログでも秘匿する。callbackでは外部画像や分析スクリプトを読み込まず、`Cache-Control: no-store`・`Referrer-Policy: no-referrer`を付け、処理後は機密クエリのないURLへ移動する。認証情報をlocalStorage・sessionStorageや画面サンプルへ保存しない。

全役割共通で、アイドル期限は本人の最後の操作から24時間、絶対期限はログインから最長1か月に確定した。サーバーは両方を確認し、先に到達した時点で失効させる。自動ポーリング・バックグラウンド更新は本人の操作に数えず、本人が操作しても絶対期限は延長しない。期限切れは再度Google認証へ進む。期限を延ばすためにGoogle refresh tokenを保存しない。重要操作の再認証条件は引き続き未決。

「1か月」の計算は実装上の具体化案として、日本時間でログインした翌月の同日・同時刻（翌月に同日がなければ月末の同時刻）を期限とし、確定した期限をUTCで保存する。これはユーザーの期間回答を具体化する技術案であり、30日固定との回答を得たものではない。

利用停止・退職・所属変更・権限縮小・Google関連付け変更では、当該利用者の全アプリセッションを失効させ、次のAPI操作から旧権限を拒否する。毎回の業務APIで利用者状態・所属・権限改訂を確認する。現在の端末だけ／全端末のログアウトもサーバー側で失効させる。

アプリからのログアウトはGoogle全体からのログアウトではない。Google側のパスワード変更・アカウント停止・連携解除が既存アプリセッションを即失効させるとは仮定しない。確定したセッション期限に加え、侵害時の連絡、アプリ側の緊急停止、必要ならGoogleのセキュリティイベント連携を運用で定める。

## 6. 二段階認証・回復・アカウント変更

二段階認証・パスキー・パスワード回復はGoogleで行い、アプリ内にOTP入力・TOTP登録・復旧コード発行・パスワード再設定APIを作らない。会社管理者のGoogle側の二段階認証は必須、管制担当・閲覧者・警備員は推奨に確定した。会社管理者の必須条件をGoogle WorkspaceのポリシーやGoogleが提供する検証可能な情報で満たせるか確認する。OIDC成功、`email_verified`、`hd`、アカウント選択だけをMFA実施の証明にしない。利用可能な認証情報・再認証手段の実証は着手前の条件とする。

2026年10月8日に確認した技術候補として、Googleの[Security bundle](https://developers.google.com/identity/siwg/security-bundle)には認証方法を示す`amr`とGoogle側の最終認証時刻を示す`auth_time`がある。公開・検証済みアプリで追加設定と要求が必要で、要求しても`amr`がない場合がある。検証済み`amr`に`mfa`が含まれる場合は、そのGoogle認証時の多要素認証の証拠として扱えるが、欠落をMFA未実施・実施のどちらにも推定しない。会社管理者の必須方針に対応する確認不能時の扱いと、検証環境での利用可否を実装前に具体化する。アプリセッションの期限切れからGoogleログインへ戻っても、既存のGoogleセッションが使われることがあり、毎回のパスワード・二段階認証入力を要求できるとは仮定しない。

Googleアカウントを回復できない場合、GoogleまたはWorkspace管理者の回復手順を案内する。別Googleアカウントへの付け替えが必要なら、会社管理者による本人確認・承認後に旧関連付け・全アプリセッションを無効にし、新しい7日間の招待で再関連付けする。会社管理者自身の変更は別の会社管理者が承認し、ほかにいなければ運営者が承認する。全会社管理者がログインできない場合の復旧・管理者交代は、運営者が会社と本人を確認して対応する。運営者の対応は理由・対象会社・本人確認・承認・結果を監査し、通常の業務APIで最後の管理者保護を解除する救済経路にはしない。独自の救済パスワードは設けない。

| 既存URL | Google方式での画面内容 |
| --- | --- |
| `/login`・`/guard/login` | Googleログインの入口。モック閲覧リンクを認証ボタンと分ける |
| `/account/activate` | 招待の確認と初回Google関連付け |
| `/account/reset` | Googleアカウントの回復案内。自システムで再設定しない |
| `/account/mfa` | Google側の二段階認証・セキュリティの案内。アプリ内で登録・確認しない |
| `/account/security` | Google関連付けの表示、変更時の問い合わせ、アプリセッションのログアウト |

## 7. 着手前に決める運用とGoogle側の設定

- 個人Gmail・会社Workspaceの許可範囲は確定。実際の本人用Googleアカウントの準備状況、持たない人への案内、Workspaceと所属会社の確認手順を決める。本人用メールが使えるという既存回答だけではGoogleアカウント所有を確認したことにならない。
- 招待メールは会社管理者の登録した本人Googleメール宛て、発行から7日間に確定。関連付け変更と最初の管理者登録・全管理者利用不能時の担当も上記のとおり確定。残る本人確認の資料・記録、誤宛先・不達時の対応、再有効化、運営者への連絡と審査手順を具体化する。対象外の外部メールGoogleアカウントを今後許可する場合は、別途方針変更と本人確認の設計が必要。
- 会社管理者のGoogle側の二段階認証必須を技術的に強制・検証する方法と、確認不能時の扱い。管制担当・閲覧者・警備員は推奨。確認できるまで必須要件を達成済みとしない。
- セッションは操作なし24時間・最長1か月に確定。重要操作の再認証、全端末失効の運用、Google障害・端末紛失・アカウント侵害時の連絡と業務継続手順を決める。
- 環境別のGoogle Cloudプロジェクト／Web application OAuthクライアント、固定redirect URI、クライアント秘密の保管・交換。設定値は実装時に追加し、現段階の`.env`等へ仮の秘密を書かない。
- 複数社・個人Googleアカウントを対象にする場合は、1つのWorkspace組織に限定するInternal設定では足りない。External等の対象設定、テスト利用者、公開状態、同意画面、ドメイン所有確認、プライバシーポリシー、Googleの検証要否を公開前に確認する。[Googleの公開・ブランド確認条件](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification)

## 8. 今後の受入確認

正常ログインに加え、未招待・停止・期限切れ招待・招待再利用・メール不一致・関連付け重複、改ざんIDトークン・別`aud`／`iss`・期限切れ・nonce/state不一致・PKCE不一致・コード再送・外部復帰先を拒否する。Google認証取消や通信失敗でも利用者・セッションを中途半端に作らない。

招待の発行から7日間の期限境界、再招待後の旧リンク拒否、承認者別の関連付け変更を確認する。会社管理者の自己承認を認めず、管理者本人の変更は別の管理者、ほかにいなければ運営者が承認すること、全管理者利用不能時は運営者による会社・本人確認の記録が必要であることを確認する。承認後の旧関連付け・全セッション失効と新招待の発行、未承認での付け替え拒否、最後の管理者保護を迂回する通常業務APIがないことも確認する。

個人Gmailと会社Workspaceを受け入れ、Gmailではなく有効な`hd`もないGoogleアカウントを拒否することを確認する。全役割で操作なし24時間・最長1か月の各境界、月末の期限計算、自動更新ではアイドル期限が延びず本人の操作でも絶対期限が延びないことを確認する。会社管理者の二段階認証必須について、採用する検証方法と確認不能時の扱いを実証し、ほかの3役割の推奨方針と混同しない。

既知の`sub`のメール変更で同じ利用者へ戻ること、同じメールの別`sub`を自動関連付けしないこと、停止・降格・移籍後の既存セッション拒否、会社・拠点・本人の認可、ログアウトの範囲、共有端末・スマートフォンでのアカウント選択を確認する。フォーム・API・DB・ログ・ビルド成果物に利用者パスワード・Google復旧コード・クライアント秘密がないことも確認する。

これらは今後の実装で行う検証であり、現在のモックで合格した結果ではない。関連する受入条件は[要件書](MVP_REQUIREMENTS.md)、[API契約](MVP_API_CONTRACT.md)、[実装引き継ぎ](AI_IMPLEMENTATION_HANDOFF.md)に記載する。

Google側の操作案内: [二段階認証](https://support.google.com/accounts/answer/185839)、[Googleアカウントの回復](https://support.google.com/accounts/answer/7682439)。公式資料の確認日: 2026年10月8日。
