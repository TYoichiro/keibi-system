# 初回の業務API契約案

作成日: 2026年10月8日（日本時間） / 版: 0.4 / 状態: Google専用・許可対象・役割別MFA・セッション期限・招待方法/期限・変更承認者と初期/復旧担当は確定、URL・契約詳細は実装前の提案

現在の認証・業務APIは未実装。この資料のURL、JSON名、数値上限は設計案であり、実装開始の指示ではない。[要件書](MVP_REQUIREMENTS.md)のF01〜F09を、画面とAPIの担当AIが同じ解釈で実装できるよう具体化する。業務条件と権限は要件書、状態と例外は[状態遷移案](MVP_STATE_TRANSITIONS.md)を基準にする。Google OAuth 2.0 / OIDC専用、個人Gmail＋会社Google Workspace、会社管理者のGoogle側二段階認証必須と他3役割の推奨、本人操作なし24時間・最長1か月のセッションは確定済み。Q09の招待・MFA確認/強制・本人操作識別等の実装/運用、公開期間Q07、資格条件Q06等が決まった後に詳細契約を確定する。認証の検証基準は[Googleログイン設計](GOOGLE_AUTH_DESIGN.md)を参照する。

## 1 共通契約

| 項目 | 提案 |
| --- | --- |
| 認証 | サーバーでGoogleのIDトークンを検証し、連携済み`iss`・`sub`と有効な所属から発行したアプリのCookieセッションをAPIで検証。有効な会社所属・役割・拠点・本人対応を毎回確認する。ブラウザからGoogleトークンを直接業務APIの権限として受け付けない |
| セッション期限 | 全役割で最終本人操作から24時間、またはログイン完了から最長1か月の早い期限で失効する。自動ポーリングで更新せず、絶対期限を通常操作で延長しない |
| 会社の決定 | 業務APIの会社は認証済み所属から決定。本文・クエリの`companyId`で切り替えない |
| 拠点の指定 | 管理者の自社内操作に`branchId`を使う。管制・閲覧者が範囲外を指定したら拒否し、全拠点検索へ広げない |
| 本店条件 | 支店追加と隊員登録枠増加は、本店に有効所属する会社管理者だけに許可する。会社管理者の役割だけでは許可せず、支店所属の管理者も拒否する |
| 会社共通の取引先 | `clients`は会社共通で`branchId`を持たない。管制/閲覧者の一覧・詳細・候補・件数は所属拠点の有効な利用関係へ限定する技術案。会社管理者は自社全体を参照可能。本体の編集者は未決で会社管理者のみの案 |
| 入力 | JSONは許可した項目だけ。未知のキー・不正な状態・型・関連IDを拒否。更新日時、操作者、公開状態を自由入力させない |
| ID | 内部IDはUUID。`G004`等の業務コードとは区別。実データの本人IDを固定しない |
| 日付・日時 | 日付は`YYYY-MM-DD`。日時は秒精度のISO 8601、明示的なオフセットを必須とする。例: `2026-10-04T22:00:00+09:00`。表示・勤務日は日本時間 |
| 更新競合 | 更新対象の`expectedVersion`を必須とし、DBの現在値と一致した場合だけ更新。勤務枠の下書き・公開操作は共通の枠の更新番号で競合検出 |
| 再送 | 業務の作成・更新・確定・取消に`Idempotency-Key`を必須とする提案。キーは操作ごとに生成するUUID v4。1操作の再送には同じキーと同じ入力を使う |
| 応答 | 成功は`{ "data": ... }`。一覧は`data`配列と`page`, `pageSize`, `total`。業務エラーは下記の形 |
| キャッシュ | 既存のAPIの`Cache-Control: no-store`を維持。本人・役割別の応答を共有キャッシュに載せない |
| 追跡 | 既存のサーバー生成`X-Request-Id`を使う。クライアントのキーを監査用のリクエストIDとして信頼しない |

`expectedVersion`は作成時には不要、既存対象の変更時には必要。作成は201、取得と変更は200を返す案とする。最初の会社管理者登録は、運営者が会社・本人を確認する限定手順で行う。全会社管理者がログイン不能となった場合のアプリ利用の復旧/管理者交代も同じ責任分担で扱い、一般公開の自己登録/復旧APIにしない。Googleパスワード回復はGoogleに案内し、Googleアカウントを本システムで発行しない。

既存`GET /api/health`の応答は変更対象に含めない。既存のOrigin・CSRF・容量・頻度制限のエラー形がこの案と異なるため、画面はHTTP状態と`X-Request-Id`でも処理する。業務APIの追加に合わせた統一は別途検討し、既存対策を緩めない。

### 1.1 数値と正規化の提案

業務上の上限が確認済みという意味ではない。試験運用の人数・検索量・既存番号体系を確認してから確定する。

| 入力 | 提案値・検証 |
| --- | --- |
| 名称・氏名 | 前後空白を除き1〜100文字。氏名の重複を許可。姓名分割・読み仮名は初回に必須としない |
| 会社・拠点・隊員・現場・取引先・資格のコード | 1〜32文字、英数字・`_`・`-`。大文字へ正規化し会社内で一意。退職・終了したコードの再利用は行わない提案 |
| 場所・集合場所 | 1〜300文字。勤務で使う場所を保持し、隊員の私住所は収集しない |
| 指示・内部メモ・配置条件の補足 | 各0〜2,000文字。HTMLとして保存・描画しない。非公開メモを公開指示へ自動コピーしない |
| 変更理由 | 改訂・取消・状態変更・権限変更・増枠は1〜500文字。通常の連絡先訂正等の必須化は画面仕様と合わせる |
| 業務電話 | 任意、最大50文字。国内固定電話だけの形式に限定せず、連絡手段の確認を別に行う |
| メール | 業務連絡先・招待先・Googleからの検証済みメールを別項目で扱う。メールを本人識別キーにせず、Google本人は正規化した検証済み`iss`・`sub`で解決する。業務メール編集でGoogle連携を変更しない |
| 人数・配置配列 | 必要人数は1〜1,000、配置隊員は最大1,000名、同一隊員を重複させない提案。資格必要人数は1以上・必要人数以下 |
| 拠点登録上限 | 初期10。増枠は現在値より大きい整数。技術上限の案は10,000、実人数・費用計画と合わせて確認する |
| 文字数 | 上記はUnicodeコードポイント数の案。フロントとAPIの数え方を合わせ、別途既存の本文容量制限も適用 |
| ページング | `page`は1以上、`pageSize`は既定20・最大100。`total`は認可済みの範囲だけを数える |
| 検索 | `q`は最大100文字、許可した検索・ソート項目だけ。安定した並び順として同値時に内部IDを使う |
| 予定の検索期間 | `from`と`to`の日付を必須、両端を含む。1回最大93日、既定の画面検索は7日。範囲外は400、勝手に切り詰めない |

契約開始・終了日は両方入力または両方未入力。終了日は当日の日本時間を含む。勤務全体が期間内かの判定は開始・終了日時で行い、夜勤の翌日部分も確認する。最大勤務継続時間・将来何日先まで作成できるかは業務確認後に定め、上記93日を勤務時間の上限と取り違えない。

### 1.2 エラー

```json
{
  "error": "VERSION_CONFLICT",
  "requestId": "サーバー生成のID",
  "fieldIssues": [],
  "retryable": false
}
```

`fieldIssues`は入力の項目パスと文言コードのみ。秘密・SQL・入力全文を返さない。未知の対象IDの存在確認より認可を先に行い、別会社・別拠点・別本人の対象と存在しない対象は同じ404応答にする。

| HTTP | 業務コード例 | 画面で行うこと |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | 項目エラーと入力値を残す |
| 401 | `SESSION_REQUIRED` | 保存前の入力を扱う方針に従い、再ログインを案内。未認証で自動再送しない |
| 403 | `OPERATION_FORBIDDEN`, `AUTH_POLICY_REQUIRED` | 操作不可を表示。対象の存在・他社情報を説明に含めない。会社管理者のGoogle側二段階認証必須、他3役割の推奨は確定済み。MFA判定はQ09で確認/強制手段と`amr`欠落時の扱いを確定・実証してから用い、OIDC成功だけからMFA未実施/実施を推測しない |
| 404 | `NOT_FOUND` | 許可範囲で取得できないことを表示 |
| 409 | `VERSION_CONFLICT`, `DUTY_OVERLAP`, `QUOTA_EXCEEDED`, `STATE_CONFLICT`, `IDEMPOTENCY_CONFLICT` | 最新状態を取得して差分を確認。勝手に上書きしない |
| 409 | `DUTY_CONDITIONS_NOT_MET` | 人数・資格・責任者等の認可済み確認結果を表示。下書きと旧公開版を保持 |
| 413 / 415 | 既存の容量・JSON形式のエラー | 入力・送信形式を案内 |
| 429 | 既存の頻度制限のエラー | `Retry-After`に従い待機。連続送信しない |
| 500 / 503 / 応答未受信 | `INTERNAL_SERVER_ERROR`, `SERVICE_UNAVAILABLE`等 | 保存結果が不明なら操作照会。同じ処理を別キーで作り直さない |

HTTPメソッドだけで二重作成防止は完成しない。本資料の再送記録・トランザクションはアプリケーション側の追加契約である。[HTTPの冪等性と状態コード（RFC 9110）](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

## 2 操作とURLの案

### 2.1 Google認証とアプリのセッション

以下は認証の専用経路であり、業務作成の`Idempotency-Key`や`expectedVersion`は使わない。短命のログイン取引・招待の一回限りの消費・セッション失効で再使用を防ぐ。

| 要件 | メソッド・URL案 | 操作・注意点 |
| --- | --- | --- |
| F02・F03 | `GET /api/auth/google/start` | 同一オリジンのログイン開始から、サーバーで短命の`state`・`nonce`・PKCE（S256）と開始ブラウザとの対応を作りGoogleへ誘導。スコープは`openid email`。復帰先と招待参照はサーバー側で検証・保持し、許可したアプリ内パスだけへ戻る |
| F02・F03 | `GET /api/auth/google/callback` | Googleのコードをサーバーで交換し、署名・`iss`・`aud`・`exp`・`nonce`と`state`・PKCE・開始ブラウザとの対応を検証。連携済み本人または検証を完了した有効な招待だけにアプリのセッションを発行する。失敗時に利用者や会社を新規作成しない |
| F02 | `POST /api/auth/logout` | 現在のアプリセッションをサーバーで失効してCookieを削除。Google全体からのログアウトと区別する。既存Origin・CSRF対策を適用 |
| F02 | `POST /api/auth/logout-all` | 本人の全アプリセッションをサーバーで失効。既存Origin・CSRF対策を適用 |

GoogleからのクロスサイトGETコールバックは必要な専用経路だけに限定し、Origin/CSRF検証をAPI全体で解除しない。開始ブラウザに結び付く`state`等を必須とし、期限切れ・再使用・別ブラウザの取引を拒否する。GoogleのIDトークン・アクセストークン・Authorization Codeを処理後の画面URLや応答、`localStorage`、ログ・監査へ出さず、初回はリフレッシュトークンを要求・保存しない。認証コード等を含むcallbackのクエリはAPI・プロキシ・監視で秘匿し、処理後は機密クエリのないURLへ移動する。本番のアプリCookieには`HttpOnly`・`Secure`・`SameSite=Lax`を設定し、ログイン完了時にセッションを新規発行する。

ログインでは、サーバーで署名・issuer等を検証したIDトークンの`email_verified`が真であり、個人Gmailまたは`hd`がある会社Google Workspaceであることを確認する。非Gmailかつ`hd`なしの外部メールGoogleアカウントは初回に拒否し、追加本人確認で許可する経路は設けない。将来対象を追加する場合だけ別途追加確認を設計する。`hd`は署名検証済みのclaimsから取得し、リクエストのドメイン指定を信用しない。会社の管理ドメイン一致ルールはQ09で具体化し、`hd`だけで会社・役割を付与しない。

未連携利用者の初回はGoogle本人認証と招待対象の検証を両方必要とする。招待対象と検証済みGoogleメールを照合し、メール一致を使った既存利用者の自動連携や再連携を設けない。認証キャンセル・Google障害・無効な取引はログイン画面へ安全に戻し、詳細な会社/利用者の存在を公開しない。

招待は、会社管理者が登録した本人Googleメール宛てにリンクを送り、発行から7日間・一度限り有効とする。暗号学的に安全な乱数の招待トークンを生成し、ハッシュ・発行/期限・使用/無効化状態をサーバー側で管理する。期限は発行から168時間後の瞬間をUTCで保存する設計案とし、期限以上では拒否する。再招待では旧リンクを無効にして新しい7日間のリンクを発行し、旧リンクの消費と競合しても両方の初回連携を成立させない。メールの送信結果と招待使用を分け、不達/誤宛先の対応とメール配信基盤は別途具体化する。

Google連携変更は会社管理者が本人確認の上で承認する。会社管理者自身の変更は同じ会社の別の会社管理者、ほかにいなければ運営者が承認する。申請者が自己承認できるAPIにせず、最新の承認権限と本人確認結果をサーバーで検証する。承認後は旧Google連携と全アプリセッションを無効にし、新しい本人Googleメールに7日間の招待を発行する。通常のメール編集や`iss`/`sub`直接入力で変更させない。申請/承認/再招待の具体的なURL・保存項目と競合契約はQ09で定める。

アプリセッションは全役割で最終本人操作から24時間、またはログイン完了から最長1か月の早い期限を適用する。1か月は日本時間の翌月同日時、該当日がない場合は月末同時刻とする技術案（例: 10月31日09:00→11月30日09:00）。UTCで保存した期限とサーバーの現在時刻を比較し、期限以上のリクエストには401を返して、本人操作日時の更新で復活させない。有効なセッションの認可済み本人操作だけがアイドル期限を更新し、自動ポーリング・自動再取得・バックグラウンド通信は更新しない。本人操作として扱うAPI/画面イベントの識別と更新方式はQ09で具体化し、クライアントが送る時刻を根拠にしない。通常操作で絶対期限を延長せず、満了後は再度Google認証する。

パスワードログイン・新規パスワード登録・パスワード再設定・独自TOTP登録/検証・MFA復旧コード発行のAPIは作成しない。`/account/reset`はGoogleアカウント回復、`/account/mfa`はGoogleのセキュリティ設定への案内として扱う。

### 2.2 業務操作

管理者=会社管理者、管制=所属拠点の管制担当、閲覧=所属拠点の閲覧者。表中の役割にも要件書3章の項目制限を適用する。警備員の取得は`/api/me/*`に分ける。

| 要件 | メソッド・URL | 操作・許可範囲 |
| --- | --- | --- |
| F02・F03 | `GET /api/me` | 有効な本人の役割・所属・隊員対応と利用できる機能。全役割 |
| F01 | `GET /api/branches` | 管理者は自社、その他は本人の所属名称だけ。登録人数・枠の詳細は管理者のみ |
| F01 | `POST /api/branches` | 支店と初期登録枠を同時作成。本店所属会社管理者のみ。本店種別や操作者の所属を本文で指定させない |
| F04 | `PATCH /api/branches/:id/officer-limit` | `limit`, `expectedVersion`, `reason`。本店所属会社管理者のみ、増加のみ |
| F03 | `GET /api/memberships` | 自社の利用者一覧。管理者のみ |
| F03 | `POST /api/memberships` | `invitationEmail`として本人Googleメール、表示名・役割・拠点・必要なら隊員対応を指定し事前登録する。管理者のみ。発行から7日間・一度限りの招待リンクを本人Googleメール宛てに送る。Googleアカウント作成やメール一致によるGoogle連携は行わない |
| F03 | `PATCH /api/memberships/:id` | 有効状態・役割・所属・隊員対応の変更。管理者のみ。最後の管理者を失う更新を拒否 |
| F04 | `GET /api/officers`, `GET /api/officers/:id` | 管理者・管制・閲覧。閲覧用の公開項目を区別 |
| F04 | `POST /api/officers`, `PATCH /api/officers/:id` | 基本情報・在籍状態。管理者・管制。登録枠と状態変更の影響を確認 |
| F04・F07 | `GET /api/qualifications` | 自社の資格マスタ。管理者・管制・閲覧に公開範囲を分ける |
| F04・F07 | `POST /api/qualifications`, `PATCH /api/qualifications/:id` | 資格マスタの登録・利用停止。管理者のみの提案、Q06で確定 |

| F05 | `GET /api/clients`, `GET /api/clients/:id` | 管理者は自社の会社共通取引先全体、管制/閲覧は所属拠点の有効な利用関係があるものだけ。候補/件数にも同じ制限を適用する技術案。窓口公開項目は別途確認 |
| F05 | `POST /api/clients`, `PATCH /api/clients/:id` | 会社共通の名称・コード・業務窓口・利用状態。`branchId`を受け付けない。編集者はユーザー確認待ちで、会社管理者のみを許可する案 |
| F05 | `PUT /api/clients/:id/branch-access` | 取引先を利用する自社拠点の関係を会社管理者が登録する技術案。保存表現は`client_branch_access`。既存現場がある関係の解除/無効化条件は未決で、詳細契約の確定後に対応 |
| F05 | `GET /api/sites`, `GET /api/sites/:id` | 管理者・管制・閲覧。内部メモ等は項目制限 |

| F06・F07 | `GET /api/duty-slots`, `GET /api/duty-slots/:id` | 日付・現場で勤務枠一覧、下書き・公開版を区別した詳細。管理者・管制・閲覧 |
| F06 | `POST /api/duty-slots` | 勤務枠と初回下書きを同時作成。管理者・管制 |

| F06・F07 | `POST /api/duty-slots/:id/confirm` | 下書き版ID・枠の更新番号を指定して確定または再確定。条件・現時点の権限を再確認 |
| F06 | `POST /api/duty-slots/:id/cancel` | 勤務枠全体の取消。`expectedVersion`, `reason`。隊員だけの解除は改訂で処理 |
| F07 | `GET /api/assignment-summary` | 認可範囲の指定日の公開人数・下書き不足等を別フィールドで集計。勤務中人数は返さない |
| F08 | `GET /api/me/officer` | 警備員本人の基本情報・資格確認情報。内部メモを返さない |
| F08 | `GET /api/me/duties` | 本人の予定と取消概要。日付範囲必須。下書き・他人の予定を返さない |
| F08 | `GET /api/me/duties/:slotId` | 本人の最新公開予定または取消概要 |
| F08 | `GET /api/me/duties/:slotId/site` | 対象勤務の本人の担当・公開期間内だけ、版に保存した現場情報。現場IDだけでは許可しない |
| F09 | `GET /api/audit-events` | 許可された会社・拠点・対象・項目に限定した履歴。閲覧者不可、警備員には直接提供しない |
| 共通 | `GET /api/operations/:key` | 操作者本人の再送識別子の結果照会。現在の権限で再認可。別利用者のキーは404 |

勤務開始後の管制による下書き編集・破棄を含めた権限は状態遷移案の確認事項に従う。終了済み勤務の訂正、取消済み勤務の再開、拠点/会社の停止、アカウント再有効化とGoogle連携変更は汎用PATCHで受け付けない。連携変更の承認者と運営者の初期/全管理者ログイン不能時対応は確定済みで、申請・本人確認・承認・失効・再招待の専用契約を具体化する。Googleの`iss`・`sub`はクライアント入力や通常の利用者編集で上書きさせない。

## 3 保存入力と取得項目

共通の`expectedVersion`、変更理由と権限検証は省略して記す。PATCHでは未指定項目は維持、任意文字列の`null`は削除、空文字は任意欄のみ未設定へ正規化する提案。必須欄の`null`は拒否。PUTの配列は全体置換であり、欠落した配置・資格をそのまま残さない。

| 対象 | 保存可能な項目の案 | サーバー専用・注意点 |
| --- | --- | --- |
| 支店 | `code`, `name`, `businessPhone` | `companyId`, 本店種別, 初期上限10はサーバーが決定 |
| 利用者の事前登録・招待 | `invitationEmail`（本人Googleメール）, `displayName`, `branchId`, `role`, 警備員なら`officerId` | 内部利用者IDと所属、サーバー発行から7日間の招待期限をサーバーで決定。Googleの`iss`・`sub`は検証後の認証処理だけで登録。パスワード・ハッシュ・MFA秘密・復旧コードを受け付けず、招待秘密・Googleトークンを業務応答/監査へ返さない。送信/使用/再招待による無効化・Google連携・利用停止を分ける |
| 隊員 | `code`, `name`, `branchId`, `status`, `businessPhone`, `businessEmail`, `employmentType`, `serviceArea`, `internalMemo` | 在籍は`active / leave / retired`。所属異動の履歴・未終了配置対応は要確認 |
| 隊員資格 | `qualificationId`, `verificationStatus`, `validFrom`, `validThrough` | 確認状態と期間の詳細はQ06。確認者・確認時刻はサーバー決定 |
| 会社共通取引先 | `code`, `name`, `status`, `contactName`, `businessPhone`, `businessEmail` | 自社の共通マスタ1件。`branchId`を受け付けず、会社IDは認証済み所属から決定。本体の編集者は管理者のみの案・ユーザー確認待ち。停止時の複数拠点の現場/配置への影響を確認 |
| 取引先の拠点利用関係 | `branchIds`（自社の利用拠点）の案 | 会社管理者が`client_branch_access`へ同社の関係を登録する技術案。管制/閲覧者の公開対象を決める。無効化/解除と既存現場の整合条件は未決 |
| 現場 | `code`, `name`, `branchId`, `clientId`, `securityType`, `location`, `meetingPoint`, `status`, `instructions`, `internalMemo`, `contractFrom`, `contractThrough` | 状態は`planned / active / paused / closed`。標準人数・時間を追加する場合は勤務版への初期コピーのみ |
| 下書き | `dutyDate`, `startsAt`, `endsAt`, `requiredCount`, `assignments`, `qualificationRequirements`, `siteSnapshot`, `availabilityCheck`, `travelRestCheck`, `reason` | `siteSnapshot`は許可した現場名・場所・集合場所・指示・業務窓口だけ。公開時の氏名等はサーバー取得。確認者を自由指定しない |

`assignments`は`officerId`と`isLeader`、`qualificationRequirements`は`qualificationId`と`requiredQualifiedCount`の配列案。現場責任者人数の正式条件・資格判定・確認記録の単位はQ06で決定する。必要人数未充足の下書きは保存可能、確定は不可。

役割の値は`company_admin / dispatcher / viewer / guard`、取引先・資格マスタの利用状態は`active / inactive`、資格の確認状態は`unverified / verified / invalid`の契約案とする。認証基盤の管理者権限をこの業務役割へ自動対応させない。

資格一覧の置換で指定しなかった資格は、現在の有効な関連から外す。過去の確認情報を物理削除せず履歴に保持し、無効化と同様に未終了公開勤務への影響を再確認する。現場・隊員の`branchId`変更は一般の編集と区別し、関連現場・未終了勤務・履歴・枠の整合性を満たす決定済み手順がある場合だけ許可する。取引先本体に所属拠点変更は設けず、利用拠点の関係を管理する。異動後の過去履歴閲覧はユーザー回答待ちとし、現在の所属だけで旧履歴の範囲を自動決定しない。

管制/閲覧者の取引先参照は、会社管理者が明示登録した所属拠点の有効な`client_branch_access`で制限する技術案。現場がまだない拠点でも有効な関係があれば候補取得を許可し、同社という理由だけで無関係の取引先を公開しない。現場保存時は`site.companyId`と`clientId`の同社所属、および対象`branchId`との有効な利用関係を再検証する。会社IDを含む複合外部キーと保存時の排他で、他社参照と関係無効化との競合を防ぐ。

`availabilityCheck`と`travelRestCheck`は、確認済みか・確認時刻・確認経路の補足を表す構造案。確定時の確認者は認証済み操作者として記録し、チェックを付けただけで本人からの勤務希望が提出済みになったり法令の適合証明になったりしない。

### 3.1 役割別のDTO

| 取得先 | 含めるもの | 返さないもの |
| --- | --- | --- |
| 隊員一覧・詳細: 閲覧者 | ID・隊員番号・氏名・在籍状態・資格概要・認可済み配置 | 業務連絡先、資格の確認者等の詳細、内部メモ、認証情報 |
| 本人予定 | 勤務枠ID・公開版ID・予定日時・現場名・状態 | 下書き、他隊員ID一覧、内部メモ、非公開の変更理由 |
| 本人現場詳細 | 版の現場名・場所・集合場所・公開指示・業務窓口 | 取引先契約・単価、他隊員連絡先、他配置隊員一覧、利用者情報 |
| 本人の過去・取消概要 | 本人の勤務日時・現場名・状態 | 集合場所・指示・業務連絡先、内部の取消理由。期間はQ07に従う |
| 利用者管理・本人のGoogle連携状況 | 管理者は自社の招待先・利用状態・連携の有無、本人は自分のGoogleメールと連携日時を必要な範囲で確認 | 他社の利用者、Googleトークン、招待秘密、セッション識別子。Googleメール表示から連携を変更させない |
| 会社共通取引先: 管制/閲覧者 | 所属拠点の有効な利用関係がある取引先の基本情報と、公開が許可された窓口情報 | 無関係の取引先、他拠点の利用関係/現場/件数。検索候補や集計からの漏えいも拒否する |
| 変更履歴 | 許可された対象・項目の変更、日時・操作者の必要な表示 | セッション/招待秘密・Googleトークン、資格詳細や内部メモの権限を迂回する変更前後JSON |

管理者・管制向けのオブジェクトを丸ごと取得してフロントで隠す方法は採用しない。名前や連絡先変更後も確定済みの勤務指示と当時の表示を追跡できるよう、取得元の現在マスタと公開時スナップショットを区別する。

本人予定の状態は勤務枠全体だけで決めず、本人の公開配置との対応から取得する。勤務枠が確定のままでも、入替で外れた本人には旧版の日時・現場名・担当解除の概要を返し、新公開版の現場詳細を返さない。公開履歴のない候補者には取消概要を新しく作らない。

## 4 確定と再送結果の契約

確定成功時は`slotId`, `publishedVersionId`, `version`, `state`, `confirmedAt`を返す案。勤務枠・旧新版・有効予約・監査・再送結果を同一DBトランザクションで更新し、失敗したら旧公開版と予約も維持する。DBの排他制約違反は、許可範囲の業務エラー`DUTY_OVERLAP`へ変換する。[PostgreSQL 18の制約](https://www.postgresql.org/docs/18/ddl-constraints.html)

再送キーは会社・操作者・キーの組で一意とする提案。HTTPメソッド・操作/対象・入力ハッシュは一致検証に用いる属性として保存する。同じキー・同じ操作/対象/入力は同じ処理結果を返し、いずれかが異なると409。同じ操作者が別操作でキーを再利用しても別レコードを作らないため、`GET /api/operations/:key`の照会結果は一意になる。二つの同時リクエストが先に実行されないようDBの一意制約と処理状態を使う。確認後に更新番号が進んでも、成功済みキーの再送を新しい確定操作として扱わない。

保持期間は24時間以上を技術案とし、Q10と運用の再試行時間に合わせて確定する。保持切れのキーを新規操作として自動実行しない運用と、古いキーの拒否・照会方法を設計時に定める。結果保存に機密DTOや認証トークンを丸ごと残さず、対象IDと公開版ID等の参照を保存する。

操作照会の成功応答例:

```json
{
  "data": {
    "status": "succeeded",
    "resultRef": { "type": "duty-slot", "id": "00000000-0000-4000-8000-000000000001" }
  }
}
```

照会の状態は`processing / succeeded / failed`の案。未知・失効済み・取得不可のキーは404。404だけで未保存と決めつけず、対象の最新状態を確認する。同じキーの再送と最新取得を使い、画面は成功確認後だけ完了表示する。停止・権限縮小後には、以前の成功応答を無認可で再表示しない。

## 5 確定前に残る契約項目

- Q06: 責任者と資格マスタの管理権限、資格の有効期間判定、勤務可能・移動休息の確認単位。
- Q07: 本人現場情報の公開開始・終了、所属異動後の本人履歴。
- Q09: 許可対象、役割別MFA、セッション期限、本人Googleメール宛て7日間の招待/再招待、連携変更承認者、運営者の最初の管理者登録/全管理者ログイン不能時対応は確定済み。本人確認の具体的手順と記録、会社管理ドメイン一致、メール配信/不達/誤宛先、再招待/申請/承認の専用APIと競合処理、MFA確認/強制と`amr`欠落時、本人操作識別・更新/再認証を具体化する。非Gmailかつ`hd`なしは初回対象外で、追加本人確認は将来対象追加時だけ設計する。Google回復後もアプリの停止/失効を別管理する。既存Origin/Hono-CSRFを維持し、追加するセッション用CSRFトークンの取得/送信ヘッダーとcallback限定の統合を検証する。Argon2idやローカルパスワード経路を利用しない。
- 追加レビュー事項: コード体系、文字数・人数上限、検索期間、会社共通取引先の編集者（管理者のみの案・ユーザー確認待ち）、利用拠点関係の保存/解除と既存現場の扱い、異動後の過去履歴閲覧（回答待ち）、状態変更に対する既存配置の保護、再送記録保持。本店所属者だけの支店追加/増枠、取引先会社共通と所属拠点に関係するものだけの管制/閲覧参照は確定済み。

決定は[実装前レビュー](IMPLEMENTATION_READINESS.md)へ記録し、URL・入力・出力・エラーを確定後にOpenAPI等の機械可読な契約へ移す。今回は仕様文書の作成のみであり、ルート・スキーマ・テストは追加していない。
