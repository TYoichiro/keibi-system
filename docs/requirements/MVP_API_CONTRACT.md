# 初回の業務API契約案

作成日: 2026年10月8日（日本時間） / 版: 0.1 / 状態: 実装前の提案・未承認

現在の業務APIは未実装。この資料のURL、JSON名、数値上限は設計案であり、実装開始の指示ではない。[要件書](MVP_REQUIREMENTS.md)のF01〜F09を、画面とAPIの担当AIが同じ解釈で実装できるよう具体化する。業務条件と権限は要件書、状態と例外は[状態遷移案](MVP_STATE_TRANSITIONS.md)を基準にする。認証基盤の最終選定、公開期間Q07、資格条件Q06等が決まった後に契約を確定する。

## 1 共通契約

| 項目 | 提案 |
| --- | --- |
| 認証 | 認証基盤が発行するCookieセッションをAPIで検証。有効な会社所属・役割・拠点・本人対応を毎回確認する |
| 会社の決定 | 業務APIの会社は認証済み所属から決定。本文・クエリの`companyId`で切り替えない |
| 拠点の指定 | 管理者の自社内操作に`branchId`を使う。管制・閲覧者が範囲外を指定したら拒否し、全拠点検索へ広げない |
| 入力 | JSONは許可した項目だけ。未知のキー・不正な状態・型・関連IDを拒否。更新日時、操作者、公開状態を自由入力させない |
| ID | 内部IDはUUID。`G004`等の業務コードとは区別。実データの本人IDを固定しない |
| 日付・日時 | 日付は`YYYY-MM-DD`。日時は秒精度のISO 8601、明示的なオフセットを必須とする。例: `2026-10-04T22:00:00+09:00`。表示・勤務日は日本時間 |
| 更新競合 | 更新対象の`expectedVersion`を必須とし、DBの現在値と一致した場合だけ更新。勤務枠の下書き・公開操作は共通の枠の更新番号で競合検出 |
| 再送 | 業務の作成・更新・確定・取消に`Idempotency-Key`を必須とする提案。キーは操作ごとに生成するUUID v4。1操作の再送には同じキーと同じ入力を使う |
| 応答 | 成功は`{ "data": ... }`。一覧は`data`配列と`page`, `pageSize`, `total`。業務エラーは下記の形 |
| キャッシュ | 既存のAPIの`Cache-Control: no-store`を維持。本人・役割別の応答を共有キャッシュに載せない |
| 追跡 | 既存のサーバー生成`X-Request-Id`を使う。クライアントのキーを監査用のリクエストIDとして信頼しない |

`expectedVersion`は作成時には不要、既存対象の変更時には必要。作成は201、取得と変更は200を返す案とする。初期会社・本店・管理者の作成は通常の公開APIにせず、認証された運営者の限定した管理手順で扱う。

既存`GET /api/health`の応答は変更対象に含めない。既存のOrigin・CSRF・容量・頻度制限のエラー形がこの案と異なるため、画面はHTTP状態と`X-Request-Id`でも処理する。業務APIの追加に合わせた統一は別途検討し、既存対策を緩めない。

### 1.1 数値と正規化の提案

業務上の上限が確認済みという意味ではない。試験運用の人数・検索量・既存番号体系を確認してから確定する。

| 入力 | 提案値・検証 |
| --- | --- |
| 名称・氏名 | 前後空白を除き1〜100文字。氏名の重複を許可。姓名分割・読み仮名は初回に必須としない |
| 会社・拠点・隊員・現場・取引先・資格のコード | 1〜32文字、英数字・`_`・`-`。大文字へ正規化し会社内で一意。退職・終了したコードの再利用は行わない提案 |
| 場所・集合場所 | 1〜300文字。勤務で使う場所を保持し、隊員の私住所は収集しない |
| 指示・内部メモ・配置条件の補足 | 各0〜2,000文字。HTMLとして保存・描画しない。非公開メモを公開指示へ自動コピーしない |
| 変更理由 | 改訂・取消・状態変更・権限変更・増枠は1〜500文字。通常の連絡先訂正等の必須化は画面仕様と合わせる |
| 業務電話 | 任意、最大50文字。国内固定電話だけの形式に限定せず、連絡手段の確認を別に行う |
| メール | 認証基盤の検証・正規化に合わせる。業務連絡先とログイン識別子を別項目にし、業務メール編集でログインメールを変更しない |
| 人数・配置配列 | 必要人数は1〜1,000、配置隊員は最大1,000名、同一隊員を重複させない提案。資格必要人数は1以上・必要人数以下 |
| 拠点登録上限 | 初期10。増枠は現在値より大きい整数。技術上限の案は10,000、実人数・費用計画と合わせて確認する |
| 文字数 | 上記はUnicodeコードポイント数の案。フロントとAPIの数え方を合わせ、別途既存の本文容量制限も適用 |
| ページング | `page`は1以上、`pageSize`は既定20・最大100。`total`は認可済みの範囲だけを数える |
| 検索 | `q`は最大100文字、許可した検索・ソート項目だけ。安定した並び順として同値時に内部IDを使う |
| 予定の検索期間 | `from`と`to`の日付を必須、両端を含む。1回最大93日、既定の画面検索は7日。範囲外は400、勝手に切り詰めない |

契約開始・終了日は両方入力または両方未入力。終了日は当日の日本時間を含む。勤務全体が期間内かの判定は開始・終了日時で行い、夜勤の翌日部分も確認する。最大勤務継続時間・将来何日先まで作成できるかは業務確認後に定め、上記93日を勤務時間の上限と取り違えない。

### 1.2 エラー

```json
{
  "error": "VERSION_CONFLICT",
  "requestId": "サーバー生成のID",
  "fieldIssues": [],
  "retryable": false
}
```

`fieldIssues`は入力の項目パスと文言コードのみ。秘密・SQL・入力全文を返さない。未知の対象IDの存在確認より認可を先に行い、別会社・別拠点・別本人の対象と存在しない対象は同じ404応答にする。

| HTTP | 業務コード例 | 画面で行うこと |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | 項目エラーと入力値を残す |
| 401 | `SESSION_REQUIRED` | 保存前の入力を扱う方針に従い、再ログインを案内。未認証で自動再送しない |
| 403 | `OPERATION_FORBIDDEN`, `MFA_REQUIRED` | 操作不可を表示。対象の存在・他社情報を説明に含めない |
| 404 | `NOT_FOUND` | 許可範囲で取得できないことを表示 |
| 409 | `VERSION_CONFLICT`, `DUTY_OVERLAP`, `QUOTA_EXCEEDED`, `STATE_CONFLICT`, `IDEMPOTENCY_CONFLICT` | 最新状態を取得して差分を確認。勝手に上書きしない |
| 409 | `DUTY_CONDITIONS_NOT_MET` | 人数・資格・責任者等の認可済み確認結果を表示。下書きと旧公開版を保持 |
| 413 / 415 | 既存の容量・JSON形式のエラー | 入力・送信形式を案内 |
| 429 | 既存の頻度制限のエラー | `Retry-After`に従い待機。連続送信しない |
| 500 / 503 / 応答未受信 | `INTERNAL_SERVER_ERROR`, `SERVICE_UNAVAILABLE`等 | 保存結果が不明なら操作照会。同じ処理を別キーで作り直さない |

HTTPメソッドだけで二重作成防止は完成しない。本資料の再送記録・トランザクションはアプリケーション側の追加契約である。[HTTPの冪等性と状態コード（RFC 9110）](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

## 3 保存入力と取得項目

共通の`expectedVersion`、変更理由と権限検証は省略して記す。PATCHでは未指定項目は維持、任意文字列の`null`は削除、空文字は任意欄のみ未設定へ正規化する提案。必須欄の`null`は拒否。PUTの配列は全体置換であり、欠落した配置・資格をそのまま残さない。

| 対象 | 保存可能な項目の案 | サーバー専用・注意点 |
| --- | --- | --- |
| 支店 | `code`, `name`, `businessPhone` | `companyId`, 本店種別, 初期上限10はサーバーが決定 |
| 利用者 | `email`, `displayName`, `branchId`, `role`, 警備員なら`officerId` | パスワード・有効化トークンを業務応答や監査に返さない。招待のメール送信状態とアカウント状態を分ける |
| 隊員 | `code`, `name`, `branchId`, `status`, `businessPhone`, `businessEmail`, `employmentType`, `serviceArea`, `internalMemo` | 在籍は`active / leave / retired`。所属異動の履歴・未終了配置対応は要確認 |
| 隊員資格 | `qualificationId`, `verificationStatus`, `validFrom`, `validThrough` | 確認状態と期間の詳細はQ06。確認者・確認時刻はサーバー決定 |
| 取引先 | `code`, `name`, `branchId`, `status`, `contactName`, `businessPhone`, `businessEmail` | 初回拠点別マスタ案。停止時の現場・配置への影響を確認 |
| 現場 | `code`, `name`, `branchId`, `clientId`, `securityType`, `location`, `meetingPoint`, `status`, `instructions`, `internalMemo`, `contractFrom`, `contractThrough` | 状態は`planned / active / paused / closed`。標準人数・時間を追加する場合は勤務版への初期コピーのみ |
| 下書き | `dutyDate`, `startsAt`, `endsAt`, `requiredCount`, `assignments`, `qualificationRequirements`, `siteSnapshot`, `availabilityCheck`, `travelRestCheck`, `reason` | `siteSnapshot`は許可した現場名・場所・集合場所・指示・業務窓口だけ。公開時の氏名等はサーバー取得。確認者を自由指定しない |

`assignments`は`officerId`と`isLeader`、`qualificationRequirements`は`qualificationId`と`requiredQualifiedCount`の配列案。現場責任者人数の正式条件・資格判定・確認記録の単位はQ06で決定する。必要人数未充足の下書きは保存可能、確定は不可。

役割の値は`company_admin / dispatcher / viewer / guard`、取引先・資格マスタの利用状態は`active / inactive`、資格の確認状態は`unverified / verified / invalid`の契約案とする。認証基盤の管理者権限をこの業務役割へ自動対応させない。

資格一覧の置換で指定しなかった資格は、現在の有効な関連から外す。過去の確認情報を物理削除せず履歴に保持し、無効化と同様に未終了公開勤務への影響を再確認する。取引先・現場・隊員の`branchId`変更は一般の編集と区別し、関連現場・未終了勤務・履歴・枠の整合性を満たす決定済み手順がある場合だけ許可する。

`availabilityCheck`と`travelRestCheck`は、確認済みか・確認時刻・確認経路の補足を表す構造案。確定時の確認者は認証済み操作者として記録し、チェックを付けただけで本人からの勤務希望が提出済みになったり法令の適合証明になったりしない。

### 3.1 役割別のDTO

| 取得先 | 含めるもの | 返さないもの |
| --- | --- | --- |
| 隊員一覧・詳細: 閲覧者 | ID・隊員番号・氏名・在籍状態・資格概要・認可済み配置 | 業務連絡先、資格の確認者等の詳細、内部メモ、認証情報 |
| 本人予定 | 勤務枠ID・公開版ID・予定日時・現場名・状態 | 下書き、他隊員ID一覧、内部メモ、非公開の変更理由 |
| 本人現場詳細 | 版の現場名・場所・集合場所・公開指示・業務窓口 | 取引先契約・単価、他隊員連絡先、他配置隊員一覧、利用者情報 |
| 本人の過去・取消概要 | 本人の勤務日時・現場名・状態 | 集合場所・指示・業務連絡先、内部の取消理由。期間はQ07に従う |
| 変更履歴 | 許可された対象・項目の変更、日時・操作者の必要な表示 | セッション/再設定トークン、資格詳細や内部メモの権限を迂回する変更前後JSON |

管理者・管制向けのオブジェクトを丸ごと取得してフロントで隠す方法は採用しない。名前や連絡先変更後も確定済みの勤務指示と当時の表示を追跡できるよう、取得元の現在マスタと公開時スナップショットを区別する。

本人予定の状態は勤務枠全体だけで決めず、本人の公開配置との対応から取得する。勤務枠が確定のままでも、入替で外れた本人には旧版の日時・現場名・担当解除の概要を返し、新公開版の現場詳細を返さない。公開履歴のない候補者には取消概要を新しく作らない。

## 4 確定と再送結果の契約

確定成功時は`slotId`, `publishedVersionId`, `version`, `state`, `confirmedAt`を返す案。勤務枠・旧新版・有効予約・監査・再送結果を同一DBトランザクションで更新し、失敗したら旧公開版と予約も維持する。DBの排他制約違反は、許可範囲の業務エラー`DUTY_OVERLAP`へ変換する。[PostgreSQL 18の制約](https://www.postgresql.org/docs/18/ddl-constraints.html)

再送キーは会社・操作者・キーの組で一意とする提案。HTTPメソッド・操作/対象・入力ハッシュは一致検証に用いる属性として保存する。同じキー・同じ操作/対象/入力は同じ処理結果を返し、いずれかが異なると409。同じ操作者が別操作でキーを再利用しても別レコードを作らないため、`GET /api/operations/:key`の照会結果は一意になる。二つの同時リクエストが先に実行されないようDBの一意制約と処理状態を使う。確認後に更新番号が進んでも、成功済みキーの再送を新しい確定操作として扱わない。

保持期間は24時間以上を技術案とし、Q10と運用の再試行時間に合わせて確定する。保持切れのキーを新規操作として自動実行しない運用と、古いキーの拒否・照会方法を設計時に定める。結果保存に機密DTOや認証トークンを丸ごと残さず、対象IDと公開版ID等の参照を保存する。

操作照会の成功応答例:

```json
{
  "data": {
    "status": "succeeded",
    "resultRef": { "type": "duty-slot", "id": "00000000-0000-4000-8000-000000000001" }
  }
}
```

照会の状態は`processing / succeeded / failed`の案。未知・失効済み・取得不可のキーは404。404だけで未保存と決めつけず、対象の最新状態を確認する。同じキーの再送と最新取得を使い、画面は成功確認後だけ完了表示する。停止・権限縮小後には、以前の成功応答を無認可で再表示しない。

## 5 確定前に残る契約項目

- Q06: 責任者と資格マスタの管理権限、資格の有効期間判定、勤務可能・移動休息の確認単位。
- Q07: 本人現場情報の公開開始・終了、所属異動後の本人履歴。
- Q09: 認証基盤とセッション期限、メール変更、初回有効化/MFA復旧。既存Argon2id・Origin対策との統合。
- 追加レビュー事項: コード体系、文字数・人数上限、検索期間、取引先の拠点共有、状態変更に対する既存配置の保護、再送記録保持。

決定は[実装前レビュー](IMPLEMENTATION_READINESS.md)へ記録し、URL・入力・出力・エラーを確定後にOpenAPI等の機械可読な契約へ移す。今回は仕様文書の作成のみであり、ルート・スキーマ・テストは追加していない。
