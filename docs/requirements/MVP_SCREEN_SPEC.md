入力の形式・文字数上限・数値上限・検索期間・ページング・HTTP応答・再送識別子は[API契約案](MVP_API_CONTRACT.md)で共通化する。APIのパスやJSON形式を画面側で独自に定めない。保存項目と公開版の扱いは[データ設計案](MVP_DATA_DESIGN.md)、現在の表示と操作は[開発状況](../DEVELOPMENT.md)を参照する。

失効・競合時の未保存入力は必要な範囲で一時的に保持する案とする。個人情報を含む入力を`localStorage`等へ永続化する判断は別途行う。再ログイン先の利用者・会社が異なる場合、前の利用者の入力を復元・再送しない。認可で取得できなくなったデータを、入力保持を理由に詳細表示し続けない。

期間計算の技術案は、最長1か月をセッション作成時のJST翌月同日時、同日がない月は月末同時刻とし、サーバーでUTC日時として管理する。本人操作によるアイドル期限の更新でも絶対期限を延長しない。画面側の時計や自動再取得を認証状態の継続根拠にしない。

一覧の件数・サマリー・検索候補は同じ対象日、拠点、下書き／公開の定義でそろえる。検索条件を変えたらページ位置と選択対象を見直す。特定IDを指定したリンクが取得不可の場合、別の対象を黙って選んで「指定した詳細」として表示しない。

ブラウザ更新・戻る・直接URLでも対象を復元できるURL設計を行う案とする。業務IDや期間はAPI側でも検証し、未登録のパスには正式な案内を返す。会社・拠点・役割や固定サンプルをURLの値だけで切り替える認証を作らない。

## 4 登録・更新の入力仕様

以下の必須・任意はデータ設計案に合わせた画面仕様案。入力欄の必須表示とAPIの条件をそろえる。値の上限・許可形式・正規化・未指定値の扱いはAPI契約で一元管理し、ブラウザの`min`・`max`・`type`だけを検証として扱わない。

会社・拠点・操作者は認証した利用者から確定する項目がある。フォームに選択欄がある場合も、許可された候補だけを取得して表示する。支店追加・増枠はD03で確認済みの本店所属の会社管理者だけに許可し、画面・APIの双方で強制する。取引先は会社共通だが、管制/閲覧者の一覧・詳細・件数を所属拠点との関係で制限する。共有取引先の編集担当はD07で確認待ち。

新現場登録の候補取得の技術案は、会社管理者が取引先と拠点の利用関係を明示登録し、管制/閲覧者は自分の所属拠点に有効な利用関係がある取引先だけ取得する方式とする。現場がまだ0件でも事前に許可された利用関係があれば候補として選べる。新支店の管制へ会社共通取引先の全件を見せない。利用関係の保存単位・登録方式は技術案で、ユーザーの確認済み仕様にはしない。

在籍・資格・現場・所属の変更で未終了の確定勤務をどう保護するかはD04、開始／終了の時刻境界と旧公開版・改訂案の日時による操作権限はD06で確定する。次表の入力欄・影響確認を用意しただけで、未決の状態変更を汎用更新として許可しない。

## 5 警備員への勤務表示

G02〜G04は認証された隊員の有効配置から取得する。サンプル`G004`を本人識別に使わず、URLの隊員ID指定から本人を選び直さない。1日1勤務の固定前提にせず、勤務枠を選択して詳細を開く。同一現場の別日・日勤／夜勤も区別する。

本人の基本情報・資格基本情報と予定はAPI契約の本人専用取得経路を使う。業務監査APIを本人へ公開して履歴画面を作らず、予定APIが返す許可された変更状態・公開項目だけを示す。下表の現場情報の閲覧終了はQ07／D02の現案に対応する例であり、決定後に表示と受入期待値をそろえる。

| 本人向け状態 | 表示・リンクの案 | 表示しない内容 |
| --- | --- | --- |
| 確定予定がない | 対象期間と予定なしの案内。管制へ確認する既存手順 | 下書きの現場・隊員・人数・内部調整内容 |
| 確定済み・勤務前 | 日時・現場名・状態と、許可期間内の現場情報 | 勤怠の上番前／勤務中の断定、他隊員一覧 |
| 予定開始後・未終了 | 予定の日時と公開版を表示。開始済みの予定であることを示す案 | 打刻がないのに「勤務中」とする表示 |
| 改訂案を作成中 | 直前の公開版を表示 | 未確定の改訂内容や旧版との内部比較 |
| 改訂が確定 | 最新の公開版と更新日時。別手段の連絡を受ける運用の案内 | アプリ内通知や既読が完了したという表示 |
| 取消・担当解除 | 本人の過去概要として日時・現場名・取消状態 | 集合場所・指示・業務連絡先の詳細 |
| 予定終了後 | 本人の日時・現場名・状態の概要。勤務実績と区別する | 終了後の現場詳細。閲覧延長はQ07で別途判断 |

画面を開いたまま改訂・取消・予定終了・権限変更が起きた場合の再取得方式は実装設計で定める。少なくとも詳細表示時、画面の再表示時、利用者の更新操作で現在の許可範囲を再確認する案とする。画面に保持した古い情報を、最新確認済みの情報として表示しない。

## 6 PC・スマートフォンとアクセシビリティ

以下は初回の画面確認基準案であり、現在のモックがすべて満たしているという記録ではない。

| 対象 | 画面の基準 | 受入の確認方法 |
| --- | --- | --- |
| 画面幅 | 管理画面と本人画面をPC・スマートフォンで確認。既存レビューの幅360・390・760・1024・1440pxを継続して使う | ページ全体の横はみ出しがなく、表の横スクロールはパネル内に収まる |
| 入力 | 永続的なラベル、必須／任意、形式の説明。入力例をラベルの代わりにしない | ラベル操作で対象入力へ移動し、入力例が消えても項目名が分かる |
| エラーと成功 | `aria-invalid`・説明との関連付け。成功と進行は適切な状態通知で知らせる | 画面読み上げ・キーボードで理由と次の操作を判断できる |
| 選択と状態 | `aria-current`・`aria-pressed`等を用途に応じて使い、色以外に文字で選択・不足・取消を表す | 色が区別できない場合も現在のページ・対象・状態が分かる |
| キーボード | 検索・日付選択・隊員選択・保存・確認をキーボードだけで操作。フォーカスを可視化する | 表の選択、全フォーム、確定・取消が操作できる |
| 詳細・ダイアログ | 開いた見出し／初期入力へフォーカスを移し、閉じたら元の操作へ戻す。ダイアログなら背景の操作を制限 | 読込完了時に不意にフォーカスを奪わず、閉じた後も現在位置が分かる |
| 入力失敗 | エラー要約から項目へ移動できる。入力済み内容・変更対象を保持する | 画面上部の通知だけで失敗を知らせず、修正する項目を発見できる |
| モバイルメニュー | 開閉状態を属性と表示で示す。必要な操作を下部ナビやメニューから到達可能にする | メニュー開閉、詳細→一覧への戻り、全初回機能を操作する |
| モバイル入力 | ソフトウェアキーボード・拡大表示・下部固定メニューで入力と保存欄を隠さない | 日時・メール・電話・長文入力を実機または相当のブラウザ条件で確認する |
| Google認証への入口 | Googleボタンと案内をキーボード・画面読み上げで利用でき、認証後の戻り先が分かる。Google本人認証の入力はGoogle側で行う | アプリにパスワード/TOTP/復旧コード入力がなく、Google認証ボタンとモック閲覧リンクを区別できる |
| 長いデータ | 長い氏名・現場名・業務窓口・エラー理由・多件数を確認。折り返しや省略時の全文確認を設計する | ボタンが重ならず、確認に必要な内容が失われない |

対象の選択・送信ボタン・状態通知に、PCだけのホバー操作を必須にしない。スマートフォンでは主な操作と対象勤務の識別を優先し、次期のリンクで必要な操作を埋もれさせない。
