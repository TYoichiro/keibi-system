2026年10月8日のユーザー指定により、全役割が本人のGoogleアカウントでログインする方式を採用する。本人認証にはOAuth 2.0とOpenID Connect（OIDC）を使い、自システムは利用者のパスワード・そのハッシュ・MFA秘密情報・復旧コードを保持しない。内部利用者ID、会社・拠点・役割・隊員との対応、アプリのセッションは業務権限のために保持する。詳細は[Googleログイン設計](GOOGLE_AUTH_DESIGN.md)を参照する。実認証は未実装であり、現在の認証画面はモックである。

同日の追加回答により、初回の許可対象を個人Gmailと会社Google Workspaceに確定した。会社管理者のGoogle側二段階認証は必須、管制担当・閲覧者・警備員には推奨とする。全役割のアプリセッションは本人操作なし24時間、ログインから最長1か月で失効する。MFAの確認・強制実装方法と、1か月の日時計算等の技術的な具体化は、確定した方針と分けて記載する。

招待は、会社管理者が登録した本人のGoogleメール宛てにリンクを送り、発行から7日間、一度だけ利用できる。再招待では旧リンクを無効にする。Google連携変更は会社管理者が本人確認の上で承認し、会社管理者自身の変更は別の会社管理者、ほかにいなければ運営者が承認する。承認後に旧Google連携と全アプリセッションを無効にし、新しい招待で連携する。最初の会社管理者登録と、全会社管理者がログインできない場合の復旧/管理者交代は運営者が会社・本人を確認して対応する。Googleパスワード回復はGoogle側で行う。

支店追加と隊員登録枠の増加は、本店に所属する会社管理者だけに許可する回答を確認済み。取引先は会社共通の1件を各拠点の現場から参照し、管制担当・閲覧者は自分の所属拠点に関係する取引先だけを参照する。拠点との利用関係の保存方式は設計案とし、会社共通の取引先を誰が編集するかは新たな未決事項として、会社管理者だけを許可する案を記載する。異動後の過去履歴閲覧は回答待ちである。

初回は、会社が隊員と現場を登録し、日別の配置を確定して、警備員本人が勤務予定を確認できるところまでを目指す。初回に実装する機能、配置に関する業務ルール、利用者ごとの権限を定める。

クラウド型のマルチテナントWebアプリとして段階的に開発する方針と、既存の画面モックを活用する方針は既定とする。初回の範囲は「ログイン・会社分離・隊員／現場管理・配置と勤務予定表示まで」とユーザーに確認済み。配置確定・基本権限・本店と登録枠の確認済み事項は4.1に、詳細な運用・認証等の未決事項は4.2に記載する。

現在は管理者・管制向け9画面と警備員向け14画面のモックがあり、業務データの保存、認証・認可、会社ごとのデータ分離は未実装。この要件書の作成によって、実装済みの範囲は変わらない。

## 1 初回に実装する機能

### 1.1 利用者と利用範囲の案

| 項目 | 初回の案 |
| --- | --- |
| 試験運用 | 1社・1拠点から開始する。会社・拠点を識別できる構造を最初から持ち、検証では2社以上のデータを使う |
| 対象業務 | 交通誘導と施設警備。ユーザー指定の「交通整備」は既存画面の交通誘導の名称に対応させる |
| 本店と支店 | 会社に本店の管理機能を1つ持たせ、担当者は個人別にログインする。本店所属の会社管理者だけが支店を1拠点ずつ追加でき、初回は追加に課金しない |
| 隊員の登録枠 | 本店・各支店にそれぞれデフォルト10人。本店所属の会社管理者だけが対象拠点の上限を増やせる。初回は増枠に課金しない。在籍・休職中を数え、退職者は履歴を残して枠から除く |
| 利用者 | 会社管理者、管制担当、閲覧者、警備員の4役割。事務担当は実際に行う業務に応じて役割を割り当てる |
| 所属 | 初回は1アカウントにつき1社・1所属拠点・1役割。複数会社への所属、複数役割の兼任、拠点間の応援配置は次期以降 |
| 操作環境 | 管理者・管制はPC中心、警備員はスマートフォン中心。両方の表示幅で利用できる |
| 初回の完了 | 登録したデータを保存でき、確定した配置が本人の勤務予定に反映され、権限のない利用者から取得・変更できない |

会社管理者は自社全体、管制担当と閲覧者は所属拠点、警備員は本人と許可された担当現場を操作・閲覧の範囲とする。隊員の業務情報とログイン用アカウントは分け、アカウントを持たない隊員も登録・配置できる。

| A05 | 配置条件 | 重複勤務、休職・退職した隊員、登録された資格条件の不足を確定時に拒否する。夜勤の重複も検出する |

| A11 | 登録枠 | 各拠点に独立した初期10人を適用し、本店所属会社管理者だけが課金なしで対象拠点を増枠できる。支店所属管理者、別会社、他役割を拒否する。別拠点の上限は変わらず、同時登録でも上限を超えない |
| A12 | Google認証・招待・認証方針 | 招待を完了した個人Gmailまたは会社Workspaceだけを許可し、`email_verified`が真でない場合、非Gmailかつ`hd`なしを拒否する。正規化した`iss`・`sub`で識別し、未招待・発行から7日到達・別本人・再使用・再招待後の旧リンク・メール一致だけの連携、不正なトークン・`state`・`nonce`・PKCEを拒否する。連携変更の本人確認と承認、管理者の自己承認禁止、承認後の旧連携/全セッション失効と新招待、運営者による初期/全管理者ログイン不能時の復旧を確認する。管理者MFA必須と他3役割の推奨を区別し、確認/強制方法の実証前は管理者受入完了としない。利用者のパスワード・ハッシュ・MFA秘密・復旧コードを保持しない |
| A13 | セッションの期限と失効 | 全役割で最終本人操作から24時間、またはログインから最長1か月の早い方に到達した時点でAPIを拒否する。期限ちょうど・月末・月をまたぐ勤務中を確認し、自動ポーリングでアイドル期限を更新しない。本人操作で絶対期限を延長せず、停止後や期限切れのセッションを操作で復活させない |

これらは今後の実装を確認する条件であり、現在のアプリが満たしていることを示すものではない。

セッションの1か月は、ログイン完了の日本時間から翌月の同日時とし、該当日がない場合は月末の同時刻とする技術案。例: 2026年10月31日09:00のログインは11月30日09:00が絶対期限。日本時間で算出した瞬間をUTCで保存し、サーバーの現在時刻が最終本人操作＋24時間または絶対期限以上なら、本人操作日時を更新する前に拒否する。本人操作として扱うAPI/画面イベントの識別方法は実装時に具体化し、クライアントが送る日時を期限の根拠にしない。

A03・A04では、同じ会社共通取引先を本店/支店の現場から参照しても重複作成しないこと、管制/閲覧者の取引先一覧・詳細・候補・件数から所属拠点に関係しない取引先や他拠点の現場情報が漏れないことも確認する。現場作成前の取引先候補は、会社管理者が拠点の利用関係を明示登録する設計案で扱う。会社共通マスタの編集者と異動後の過去履歴閲覧は、ユーザーの回答後に受入を確定する。

## 2 業務ルール

### 2.1 用語

| 用語 | 意味 |
| --- | --- |
| 会社 | データを分離する単位。テナントとも呼ぶ |
| 拠点 | 隊員・現場・管制担当の所属範囲を表す単位 |
| 勤務枠 | ある現場で行う1回の勤務。勤務日・開始終了日時・必要人数を持つ。同じ日に日勤と夜勤があれば別の枠とする |
| 配置 | 勤務枠に隊員を割り当てた記録 |
| 勤務予定 | 警備員本人に公開された確定済みの配置 |
| 勤務希望 | 本人が伝えた勤務可能日・時間・休みの希望。確定した勤務予定とは別に扱う |

### 2.2 登録と在籍状態の案

| ID | ルール |
| --- | --- |
| B01 | 隊員・現場・取引先・勤務枠・配置は会社に所属する。関連付けるデータも同じ会社であることを確認する。初回は同じ拠点の隊員と現場で配置する |
| B02 | 隊員番号は会社内で重複させない。氏名の重複は許可し、番号・内部IDで区別する。アカウントと隊員の対応は会社管理者が設定し、本人の入力だけで変更できない |
| B03 | 隊員は在籍・休職・退職を区別し、新規配置は在籍者だけを対象にする。登録枠には在籍・休職中を数え、退職者は履歴を残して枠から除く。休職・退職時は未終了の確定配置を表示して対応を求め、過去の配置を自動で削除しない。退職時は対応するアカウントも停止する |
| B04 | 休止・終了した現場に新規配置しない。準備中・稼働中の現場は配置対象とし、契約期間を登録した場合は勤務日時が期間内であることを確認する |
| B05 | 過去の配置から参照される隊員・現場を通常操作で物理削除しない。試験運用前に保存・削除の責任者と期間を決める。住所・口座・健康情報・本人確認書類等は初回の収集対象に含めない |

### 2.3 日時と配置条件の案

| ID | ルール |
| --- | --- |
| B06 | 日時は日本時間で入力・表示する。勤務日は開始日時の日付とし、終了日時には終了日も持たせる。終了は開始より後でなければ保存できない |
| B07 | 1勤務枠に同じ隊員を複数登録しない。下書きでは確定済み勤務との重複を警告し、確定時には拒否する |
| B08 | 重複は開始・終了の両日時で判定する。例として10月4日22:00〜10月5日06:00と、10月5日05:00〜09:00は重複する。終了時刻と次の開始時刻が同じ場合は時間重複に含めず、移動・休息の可否を管制が確認する |
| B09 | 必要人数は1名以上の整数とする。不足人数は必要人数から有効な配置人数を引き、0未満にならないように表示する。下書き版と公開版を区別して計算・表示し、改訂中に人数を合算しない。取消済みの配置は人数に含めない |
| B10 | 下書きは人数不足でも保存できる。必要人数を満たさない勤務枠は確定できない。人数がそろってから確定するルールは確認済み。必要人数を超える場合の警告と理由記録は案として確認する |
| B11 | 確定時は、隊員の在籍状態、同時間帯の確定配置、登録された資格条件を確認する。資格が未確認・条件不足の場合は確定しない。資格の証明内容・必要人数等の業務別の詳細条件は会社が確認し、初回の単純な条件判定を正式な業務判断の代わりにしない |
| B12 | 確定時は、配置隊員の中から現場責任者を1名選び、勤務可能であることと移動・休息の確認を記録する。現場責任者の要否と選任条件は導入会社に確認する |

### 2.4 下書きと確定と変更の案

| 状態または操作 | 管制の操作 | 警備員の表示 |
| --- | --- | --- |
| 下書き | 勤務枠・隊員・条件を登録し、保存する | 表示しない |
| 確定 | 条件を再確認して公開する。確定者・日時・版を記録する | 本人に割り当てられた勤務を表示する |
| 確定後の改訂 | 理由を記録して改訂案を作り、再確認して確定する | 改訂案の作成中は直前の確定内容を表示し、再確定時に最新内容へ切り替える |
| 取消 | 勤務枠全体の取消、または改訂による隊員の配置取消を行い、理由・操作者・日時を記録する | 取消済みと表示し、現在の有効な勤務予定から除く |

確定済みの内容を、編集途中の下書きで上書きしない。隊員の入替え・時間変更・人数変更も改訂として扱い、取消・入替え前の記録を残す。改訂を確定する際は自分の旧版を重複判定から除き、他の確定配置との重複を再確認する。

確定した勤務の集合場所・指示・業務連絡先の変更も改訂として扱う。現場の基本情報を編集しても、確定済み勤務の公開内容を自動で上書きしない。

取消は有効な確定配置を解除する。取消後の再開は新しい下書きから行い、取消記録を確定へ直接戻さない。取消・改訂案の作成だけでは本人への連絡が完了した扱いにせず、管制が別の連絡手段で伝える。

勤務日時がすでに始まっている配置の改訂・取消は会社管理者に限定し、理由を必須とする。初回は勤務予定の変更記録までを扱い、勤務実績は書き換えない。終了済みの勤務予定の訂正手順は試験運用前に決める。

### 2.5 例外時の対応の案

| 状況 | 初回の扱い |
| --- | --- |
| 人員不足・資格条件不足 | 下書きと不足表示を残し、管制が本人・応援手段・取引先と調整する。調整結果に基づいて勤務枠を見直す |
| 確定後の欠勤・交代 | 本人と管制が既存の連絡手段で確認し、配置を改訂する。本人だけで確定配置を変更・取消できない |
| 現場中止・時間変更 | 管制が取引先と確認し、取消または改訂を行って関係者へ連絡する |
| 保存中の通信失敗 | 保存の成否を再取得して示す。再送によって同じ勤務枠・配置・確定操作を二重作成しない |
| 同時編集・同時確定 | 先行する変更がある場合は競合を知らせ、最新内容を確認してから再操作する。画面側だけでなくAPI・DB側でも重複を防ぐ |
| システムを利用できない | 既存の連絡・配置確認方法に切り替える。復旧後、会社管理者が確認した内容を履歴付きで反映する |

### 2.6 勤怠を追加する際に決めること

出退勤と勤怠は次期の案とする。着手前に、打刻手段、記録漏れの扱い、休憩、日付をまたぐ勤務、遅刻・早退、修正者・承認者、確定後の訂正、集計単位を別途決める。

勤務予定と実際の打刻を分け、未報告を自動で欠勤としない。元の打刻と修正経緯を残す方針を引き継ぐ。現在のサンプルの勤務時間や丸め表示を、正式な勤怠・給与のルールとして採用しない。

### 3.3 項目と期間による制限の案

警備員に返す担当現場情報は、勤務時間・集合場所・勤務指示・業務連絡先に限定する。取引先の契約・単価、管制用の内部メモ、他隊員の私用連絡先、利用者管理情報を含めない。初回は他の配置隊員の一覧も本人向けには公開しない。

集合場所・指示・業務連絡先は、本人への配置確定後から予定終了日時まで閲覧できる案とする。配置の取消・担当解除後は取得できない。過去の勤務予定には本人の日時・現場名・状態だけを残す。終了後も現場詳細を必要とする運用は確認事項で決める。

閲覧者には隊員番号・氏名・在籍状態・配置判断に必要な資格の概要を返し、詳細な業務連絡先や資格確認情報・内部メモは返さない。変更履歴も同じ項目の制限を受け、履歴から非公開情報を取得できないようにする。

### 3.4 権限の適用方法

- 認証した利用者の有効な会社所属・拠点・役割・隊員との対応をサーバーで確認し、一覧・詳細・検索候補・件数・変更・履歴のすべてに適用する。
- 画面でボタンを非表示にするだけでなく、APIへの直接アクセスも拒否する。画面から渡された会社ID・役割・隊員IDを、そのままアクセス権の根拠にしない。
- 非公開項目はAPIの応答に含めない。対象データを推測できるIDであっても、別会社・別拠点・別隊員の権限を得られないようにする。
- 自分の権限を昇格できないようにする。最後の有効な会社管理者の通常操作による停止・降格は拒否する。全会社管理者がログイン不能になった場合の復旧/管理者交代は、運営者が会社と本人を確認する限定手順で対応する。
- アカウント停止・退職・所属変更・権限縮小後は、既存のログイン状態でも旧権限で取得・更新できないようにする。
- 運営者は通常の業務権限に含めない。初回は会社・初期管理者の事前登録と招待、アプリ利用停止、Google連携の変更審査等に必要な管理手順を限定する。GoogleアカウントのパスワードやMFAを代理でリセットせず、Google側の回復手順へ案内する。会社管理者のGoogle側二段階認証必須を維持し、運営者の管理用アクセスと合わせて確認・強制方法をQ09で具体化し、操作記録を残す。会社横断の業務データ閲覧は初回の通常機能に含めず、必要になった場合に理由・対象会社・期間・記録を持つ保守手順を別途定める。
- Googleのメールやドメインから会社・拠点・役割を自動付与しない。会社管理者が登録した所属と、検証済みGoogle識別子の対応を使う。Googleメール変更を理由に別利用者へ自動で紐付け直さない。
- Google連携変更は会社管理者が本人確認の上で承認する。会社管理者自身の変更は別の会社管理者が承認し、ほかにいなければ運営者が承認する。自己承認を許可せず、承認後は旧連携と全アプリセッションを無効にして新招待を発行する。最初の会社管理者登録も運営者が会社・本人を確認して行う。Google資格情報の回復とは分けて記録し、業務上の内部利用者IDと履歴を維持する。

既存のOrigin・CSRF・入力検証・容量制限・頻度制限等を維持する。Googleのコールバックに必要なGET経路だけを限定して統合し、`state`等で保護する。アプリのセッションとDBでの会社分離の実装詳細を定め、[Googleログイン設計](GOOGLE_AUTH_DESIGN.md)と[セキュリティチェックリスト](../SECURITY_CHECKLIST.md)の該当項目と合わせて実装・検証する。
