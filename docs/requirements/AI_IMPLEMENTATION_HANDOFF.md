# AI Agentへの実装引き継ぎ手順

作成日・更新日: 2026年10月8日（日本時間） / 版: 0.4 / 状態: 将来の実装依頼用の案

今回は実装しない。以下は別途実装開始を依頼するときの作業単位と受入の準備資料。[実装前レビュー](IMPLEMENTATION_READINESS.md)の未決事項を、AIが独自に「確認済み」へ変えてはならない。[要件書](MVP_REQUIREMENTS.md)のF01〜F09、A01〜A13を初回範囲として引き継ぐ。

全役割の個別ログインをGoogle OAuth 2.0＋OpenID Connect専用とし、ログインID・パスワードの自システム入力/保存/再設定、自社TOTP・復旧コードを採用しない方針はユーザー確認済み。Googleアカウントの本人認証と、内部利用者ID・会社/拠点/役割/隊員対応・招待・アプリセッションの管理を分ける。Google方式を反映した資料と表示見本を引き継ぐ。今回の追加回答は資料だけに反映し、実際のGoogleログイン・API・DBは実装しない。

追加回答で、初回は個人Gmail＋会社Google Workspaceだけ許可し、非Gmailかつhdなしの外部メールGoogleアカウントは対象外と確定した。Google側二段階認証は会社管理者に必須、管制・閲覧者・警備員に推奨する。全役割のアプリセッションは本人操作なし24時間で失効し、継続操作しても最長1か月。確認/強制方法とamr等の情報欠落時の扱い等の技術未決を、業務方針未決として聞き直さない。

期間の技術案: 1か月はセッション作成時点のJST翌月同日時、同日がない月は月末同時刻とし、UTC日時で保存する。ポーリング等の自動更新ではアイドル期限を更新せず、本人操作があっても絶対期限は延長しない。

招待は会社管理者が本人Googleメールへリンクを送信し、発行から7日間有効/再招待で旧リンク無効と確定した。Google連携変更は会社管理者が承認し、管理者本人は自社の別会社管理者、他にいなければ運営者が承認する。最初の会社管理者登録と全管理者ログイン不能時の復旧/交代は運営者が会社・本人を確認して対応する。Google側パスワード回復とは別の手続きで、本人確認・旧連携と全アプリセッション失効・新招待を維持する。具体的な本人確認証跡・不達/誤宛先・再有効化等はD09の詳細未決として残す。

支店追加/登録枠増加は本店所属の会社管理者だけに許可することが確認済み。取引先は会社共通1件を各拠点の現場が参照し、管制/閲覧者は自拠点に関係する取引先だけ閲覧する。共有取引先の登録/編集は会社管理者だけ・管制不可の未確認案で、編集担当と異動後の過去履歴閲覧はD07の業務詳細として確認を待つ。

取引先候補の技術案: 会社管理者が取引先・拠点の利用関係を明示登録し、管制/閲覧者は自拠点の有効な利用関係だけ取得する。現場0件でも事前許可した候補を利用でき、新支店へ全取引先を公開しない。テーブル・登録方式は開発側の案であり、ユーザー確認済みの業務回答として記録しない。

## 1 資料の読み方と判断の優先順位

1. 最新のユーザー依頼と[AGENTS.md](../../AGENTS.md)を確認し、許可された作業範囲を特定する。
2. [README](../../README.md)と[DEVELOPMENT](../DEVELOPMENT.md)で、現在の実装とモック境界を読む。
3. [MVP_REQUIREMENTS](MVP_REQUIREMENTS.md)で、確認済み事項と未決事項を分ける。
4. [実装前レビュー](IMPLEMENTATION_READINESS.md)の対象段階の決定事項を確認する。
5. [Google認証設計](GOOGLE_AUTH_DESIGN.md)、[データ設計](MVP_DATA_DESIGN.md)、[状態遷移](MVP_STATE_TRANSITIONS.md)、[API契約](MVP_API_CONTRACT.md)、[画面仕様](MVP_SCREEN_SPEC.md)の整合性を確認する。
6. [SECURITY](../../SECURITY.md)、[チェックリスト](../SECURITY_CHECKLIST.md)、[試験運用](PILOT_OPERATIONS.md)の該当項目を読む。

確認済み要件が補足資料の提案と異なる場合は、確認済み要件を優先する。要件書にも「案」と書かれた条件があるため、文書の見出しや作成日だけで承認済みと判断しない。矛盾が実装結果に影響する場合は、該当箇所と選択肢を示して確認する。別機能の未決事項は、依存しない作業まで止める理由にしない。

全体業務フローは将来の勤務希望・打刻・報告・通知も含む。フロー図にある操作すべてを初回へ追加しない。モックの氏名、人数、資格文字列、丸め設定、固定利用者を業務ルール・権限の正本にしない。

## 5 検証と完了報告

フロント変更はルートから`npm.cmd run typecheck`、`npm.cmd run lint`、`npm.cmd run build --workspace @keibi/frontend`。バックエンド・共通基盤の変更は`npm.cmd run check`。依存変更時は`npm.cmd run security:audit`も行う。業務のAPI/DBテストとE2Eを導入する場合、その実行コマンドと対象をDEVELOPMENTに追記する。

現時点の`npm.cmd run test`は既存バックエンド基盤のテストであり、上表を自動で検証するコマンドではない。新規の検証基盤が必要な段階では、API・DB・並行接続・日時制御を再現する仕組みを設計し、CIの既存チェックと合わせる。

各作業は次の項目を残す。

| 記録 | 内容 |
| --- | --- |
| 範囲 | 今回満たしたF/A/V、残る未実装の機能 |
| 決定 | 採用した案、回答日と確認者、変更した資料 |
| 変更 | 対象ファイル、マイグレーション、API/画面とモックの境界 |
| 検証 | 実行したコマンド/ケース、結果、環境、確認していない条件 |
| 運用 | 戻し方、既存データへの影響、監視・連絡の手順 |

マイグレーション失敗時の処理と戻し方は適用前に決め、データ損失を伴う戻し方を自動実行しない。コミット・PR・デプロイ・外部メールなどは、その時点で依頼された範囲に従う。実装完了と試験運用・本番公開の承認を分けて記録する。
