# 警備員管理システムのセキュリティチェックリスト

作成日: 2026年10月7日（日本時間）

警備会社ごとに利用するクラウド型Webアプリの開発・運用で確認する60項目をまとめる。警備員の個人情報、勤務予定・勤怠、取引先情報、現場の警備情報を守り、情報漏えい・不正変更・業務停止を防ぐことを目的とする。

最初に整えるのは、ログイン、会社ごとのデータ分離、利用者ごとの権限、アクセス停止の仕組み。実データの保存を始める前に設計・実装し、最初の業務APIから適用する。以下の優先度と完了条件は、このシステム向けの推奨基準であり、正式な業務ルールは導入会社と運営者で決める。

## 現在の実装と不足している対策

| 領域 | 現在の状態 | 今後の注意点 |
| --- | --- | --- |
| 業務画面 | 管理者・管制向け9画面、警備員向け14画面のモック。架空のサンプルを表示 | 固定利用者や画面の切り替えを認証・認可として流用しない。実際の個人情報をサンプルソースに入れない |
| API | `GET /api/health`のみ。業務API・業務テーブルは未実装 | 業務APIを追加するときに認証・認可・会社境界を必須にする |
| 通信・入力 | APIのセキュリティヘッダー、Origin・CSRF対策、容量・頻度制限、入力検証のヘルパーあり | これらは利用者の本人確認や他社データへのアクセス防止を代替しない |
| パスワード | Argon2idによるハッシュ処理のヘルパーあり | ログイン、セッション、MFA、招待、再設定は未実装 |
| DB・秘密情報 | DB管理者とAPI用ユーザーの分離、内部ネットワーク、秘密ファイルの管理あり | 会社ごとのデータ分離、本番DBのTLS、バックアップ・復元、外部の秘密管理は未実装・未設定 |
| 検証・公開 | バックエンドの基盤セキュリティテストとCI定義あり。本番運用は未実施 | 業務認可・テナント分離のテストと、本番構成での確認を追加する |

既存対策の詳細は[セキュリティ構成](../SECURITY.md)、画面・データの実装範囲は[開発状況と実装ガイド](DEVELOPMENT.md)を参照する。

## 優先度とチェックの使い方

| 優先度 | 対応する時期 |
| --- | --- |
| P0 必須 | 実データの投入、または対象機能の本番公開の前。該当する未完了項目がある場合は、対象機能の利用開始を待つ |
| P1 重要 | 本番運用の開始時に担当者と期限を決め、早期に実施。扱う情報の機密性・契約条件によってはP0に引き上げる |
| P2 強化 | 基本対策の後、利用規模・脅威・費用に応じて追加する |

チェックは、実装・設定だけでなく「確認」の条件を満たしたときに付ける。既存対策を含む項目も、本番構成での確認が必要なため、ここでは未チェックにしている。添付・出力・外部連携など未導入の機能は、導入時の条件として管理する。対象外とする場合は理由を記録する。

### 個人情報と現場情報

個人情報は利用目的に必要な範囲に絞り、情報の性質と漏えい時の影響に合わせた安全管理を行う。病歴等の要配慮個人情報やマイナンバーは、取得・保管の条件を別途確認する。[個人情報保護委員会の通則編](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)、[特定個人情報のガイドライン](https://www.ppc.go.jp/legal/policy/)

- [ ] **01 P0 情報の棚卸し** — 氏名・住所・連絡先・資格・教育・勤怠・勤務予定・事故報告・取引先書類ごとに、利用目的、閲覧者、管理責任者を決める。確認: 各データ項目の管理表がある。
- [ ] **02 P0 収集の最小化** — MVPで不要な本人確認書類、健康情報、口座情報、マイナンバーを集めない。追加する場合は必要性、法的条件、別管理の方法を決める。確認: フォーム・添付・自由記述にも不要な収集がない。
- [ ] **03 P0 現場の機密情報** — 鍵、暗証番号、入退場手順、警備上の弱点は特に制限する。勤務予定も無関係な人へ公開しない。確認: 担当・期間に応じた閲覧範囲があり、通知や一覧出力で漏れない。
- [ ] **04 P0 利用者への説明** — 取得目的、委託先、問い合わせ先、本人の情報確認・訂正等の受付方法を決める。必要な同意・通知を整理する。確認: 利用者向け説明と実際の処理が一致する。
- [ ] **05 P0 保存と削除** — 勤怠・教育・契約書類・監査記録ごとに法令・契約上の保存要件を確認し、削除・匿名化の時期を定める。確認: 退職・契約終了でも一律即削除せず、保存義務と不要な保管の両方に対応できる。
- [ ] **06 P1 位置情報と写真** — GPSは利用目的、取得タイミング、保存期間を決め、勤務外の追跡を避ける。写真の位置情報などの付随情報も必要性を判断する。確認: 権限拒否時の業務手順があり、不要な位置情報を保管しない。

### ログインとアカウント

認証は本人を確認する仕組みで、認可は操作できる範囲を決める仕組み。両方が必要になる。セッションはログイン状態の管理であり、有効期限と失効をサーバー側で扱う。[OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

- [ ] **07 P0 認証方式の確定** — 実績のある認証基盤・ライブラリを使い、管理者と警備員の両方で本人確認を必須にする。確認: 未ログインでは業務API・添付を取得できず、モックのログイン経路から実データに入れない。
- [ ] **08 P0 個人別アカウント** — 管制室の共有IDを避ける。招待先、所属会社、役割を発行者が確認し、招待には期限と一度だけ使える仕組みを付ける。確認: 自由登録や会社コードだけで会社の利用者になれない。
- [ ] **09 P0 管理者の多要素認証** — 運営者・会社管理者にはMFAを必須とし、復旧手順も本人確認する。確認: パスワードだけで管理者権限を使えず、MFAの解除・再登録にも確認と記録がある。
- [ ] **10 P0 パスワードの安全な保存** — 自前で保存する場合は既存のArgon2idヘルパーを使い、平文・復号可能な保存をしない。漏えい済み・一般的な弱いパスワードを拒否する。確認: DB・ログ・メールに平文がなく、強度と処理負荷を確認できる。
- [ ] **11 P0 セッションの保護** — Cookie方式では`HttpOnly`・`Secure`・適切な`SameSite`と必要最小限の送信範囲を設定する。ログイン時に識別子を更新し、アイドル期限・絶対期限を決める。確認: 古い識別子や期限切れではアクセスできない。
- [ ] **12 P0 退職と権限変更** — 退職・利用停止・所属変更・権限縮小を反映し、既存セッションやトークンも失効させる。確認: ログイン済みの端末からも旧権限で操作できない。
- [ ] **13 P0 再設定と試行制限** — パスワード再設定は期限付き・一度限りとし、再設定トークンを安全に保管する。ログイン・招待・再設定を利用者単位と接続元単位で制限する。確認: アカウントの有無が応答で判別しにくく、総当たりを抑制できる。
- [ ] **14 P2 認証の強化** — 警備員を含むMFAの拡大やパスキー、企業のSSOを検討する。確認: 共用端末・端末変更・紛失からの復旧も試し、復旧経路が認証を弱めない。

### 会社ごとのデータ分離

会社を表すテナント境界は、DBだけでなくキャッシュ・添付・非同期処理にも適用する。画面やリクエストで指定された会社IDは、その会社を利用できる証明にならない。[OWASP Multi Tenant Security](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)

- [ ] **15 P0 会社の確定** — サーバーが認証済み利用者の有効な所属を調べ、アクセス対象の会社を確定する。会社切り替え時も再確認する。確認: URL・ヘッダー・本文の会社IDを書き換えても他社へ入れない。
- [ ] **16 P0 全ての検索と更新** — 一覧、詳細、件数、検索候補、集計、更新、削除、一括処理に会社条件を適用する。確認: 未指定の会社条件で検索を実行せず、他社の存在や件数も漏れない。
- [ ] **17 P0 関連データの整合性** — 現場・隊員・配置・勤怠・報告の関連付けが同じ会社に属することをAPIとDBの制約で守る。確認: A社の配置へB社の隊員や現場を紐付けできない。
- [ ] **18 P0 DBでの分離方式** — 共有テーブルなら会社の識別と認可を全経路で強制し、PostgreSQLの行単位制御であるRLS等を含め、DB側の境界を設計する。確認: 分離方式・対象テーブル・例外経路を記録し、実際のAPI用DBロールで他社への読み書きが拒否される。
- [ ] **19 P0 接続の再利用** — RLSに会社の実行コンテキストを使う場合、同じDB接続のトランザクション内だけに設定する。API接続を管理者や`BYPASSRLS`ロールにしない。確認: 接続プールでA社の処理後にB社を処理しても会社情報が混ざらない。
- [ ] **20 P0 DB以外の分離** — キャッシュ、検索索引、ファイル、通知先、帳票ジョブに会社・利用者の範囲を持たせる。確認: ジョブ実行・ダウンロード時も認可し、権限失効後や他社のキーで取得できない。

RLSを使う場合、スーパーユーザーと`BYPASSRLS`属性のロールは制御を迂回する。テーブル所有者も通常は対象外なので、実際の接続ロールと必要な`FORCE ROW LEVEL SECURITY`を確認する。[PostgreSQL 18の行セキュリティ](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)

### 利用者の権限と運営者のアクセス

権限は明示的に許可した操作だけを認め、全リクエストで確認する。ボタンを隠すだけではAPIへの直接アクセスを防げない。[OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

- [ ] **21 P0 権限表の確定** — 運営者、会社管理者、管制、閲覧者、警備員について、閲覧・編集・承認・出力・権限管理を個別に決める。確認: 会社管理者でも他社データを扱えず、新しいAPIにも既定で拒否する設定がある。
- [ ] **22 P0 本人と担当の範囲** — 警備員は本人の勤怠・申請・報告と、許可された担当現場情報に限定する。管制担当の拠点範囲も守る。確認: 同じ会社の別隊員・別拠点へのID変更が拒否される。
- [ ] **23 P0 項目と重要操作の制限** — 私用連絡先、管理用メモ、事故の詳細などは項目単位で返却を制限する。権限変更・大量出力等には再認証や必要な承認を設ける。確認: API応答に非表示項目が含まれず、本人が自分の権限を上げられない。
- [ ] **24 P0 サポートと保守** — 運営者の会社横断アクセスは、理由・対象会社・期間を指定した専用経路に限定し、記録する。確認: サポート用共通アカウントや通常業務APIに無制限な迂回経路がない。

### APIとブラウザ

認証・認可と併せて入力形式、処理の順序、公開範囲を検証する。HTML表示とAPIにはそれぞれ必要な対策がある。[OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)

- [ ] **25 P0 サーバー側の入力検証** — 既存の`validateJson()`等を使い、型・長さ・範囲・日時・状態遷移を検証する。更新可能な項目だけを許可する。確認: 本文に`role`・会社ID・承認状態を追加しても勝手に変更されない。
- [ ] **26 P0 SQLとコマンド** — SQLはパラメーターを使い、ソート項目等は許可リストから選ぶ。入力をSQL・シェルへ連結しない。確認: 検索・CSV取込・帳票生成にも連結による実行経路がない。[OWASP SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)
- [ ] **27 P0 日報等の表示** — 利用者の入力を安全に文字として表示し、未検証のHTMLを挿入しない。リッチテキストを導入する場合は適切に無害化する。確認: 日報・メモ・通知本文に攻撃用の文字列を入れてもスクリプトが動かない。[OWASP XSS Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)
- [ ] **28 P0 CSRFと送信元** — 更新は適切なHTTPメソッドに限定し、既存Origin・CSRF対策を維持する。Cookie認証の方式に合わせてCSRFトークン等も設計する。確認: 外部サイトからの更新が拒否され、CORSの許可を認証代わりに使わない。[OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- [ ] **29 P0 通信と配信** — 本番はHTTPSで、静的HTMLにもCSP等のヘッダーを付ける。開発用Viteを公開せず、本番CSPからHMR用の例外を外す。確認: APIとHTMLの両方で設定が有効で、秘密ファイルを配信しない。
- [ ] **30 P0 過剰な処理の制限** — 本文・添付・一覧件数・検索期間・出力容量・実行時間に上限を設ける。ログインの制限は通常APIと分ける。確認: 複数APIインスタンスでも共有制限が働き、偽装した転送ヘッダーで回避できない。
- [ ] **31 P0 エラーとブラウザ保存** — エラーでSQL・内部パス・秘密を返さず、機密画面を共有キャッシュに載せない。ブラウザの永続領域へトークン・個人情報を安易に保存しない。確認: CDN・Service Workerを含むキャッシュと、ログアウト後の残存を調べる。
- [ ] **32 P0 外部通信と連携** — 外部URL取得は内部IP・クラウドのメタデータへの到達を制限する。Webhookは送信者認証、再送・重複対策を行う。確認: URLや転送先を書き換えて内部資源へ到達したり、認証なしで業務データを変更したりできない。[OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)

### DBとインフラと秘密情報

秘密情報は利用者・サービスごとに必要な範囲で管理し、発行から失効までの手順を持つ。Compose secretsのローカルファイルだけで、本番の秘密管理やディスク暗号化が完了するわけではない。[OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)、[既存の秘密ファイル管理](../SECURITY.md)

- [ ] **33 P0 DBの最小権限** — API用とマイグレーション用のDB接続を分ける。APIに必要なテーブル・操作だけを許可し、監査記録の書換え等を制限する。確認: API用ユーザーでテーブル・ロール作成や不要な操作ができない。
- [ ] **34 P0 接続と保管の保護** — 本番DBのTLSと証明書検証、DB・添付・バックアップの保存時暗号化を設定する。確認: 証明書検証を無効化せず、暗号鍵へのアクセスと復旧方法も決まっている。
- [ ] **35 P0 秘密情報の分離** — `.env`・`.secrets/`・秘密鍵・APIキーをGit、フロントエンド、画像、ログ、AIへの入力へ出さない。本番では秘密管理サービス等を使う。確認: ビルド成果物・履歴・CI出力に秘密がない。
- [ ] **36 P0 漏えい時の失効** — DB・外部サービスの認証情報と署名鍵の交換手順を用意する。漏えい時は削除だけでなく失効・再発行する。確認: 新しい秘密への切り替えと旧秘密での接続拒否を確認できる。
- [ ] **37 P0 公開範囲と管理者** — DB・管理ポートをインターネットへ公開せず、クラウド管理者にもMFAと最小権限を適用する。コンテナの非root・権限削減を維持する。確認: 外部からの到達範囲と実際の管理権限を調べる。
- [ ] **38 P0 環境の分離** — 開発・検証・本番のDB、秘密、保存先、メール宛先を分ける。検証は架空または適切に匿名化したデータを使う。確認: 開発端末やPRの検証処理が本番DB・実際の通知先へ接続しない。

### 添付と出力と通知

ファイルは形式・内容・権限・保存場所を重ねて検証する。ファイル名やURLを知っているだけで取得できる設計にしない。[OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

- [ ] **39 P0 アップロードの検証** — 必要な形式だけを許可し、拡張子・MIME・実内容、容量・数を確認する。危険な内容を隔離・検査し、ファイル名はサーバーで生成する。確認: 偽装形式・巨大ファイル・パス指定を拒否し、検査前のファイルを公開しない。
- [ ] **40 P0 ダウンロードの認可** — 非公開ストレージと認可付きの配信経路を使う。署名付きURLは期限内に第三者へ転送できる性質と、停止後の失効方法を評価する。確認: 他社ファイルへのURL発行を拒否し、期限切れは無効。重要情報は取得時にも認可する。
- [ ] **41 P0 プレビュー処理** — 添付の解析・画像変換は隔離し、処理時間とメモリーを制限する。HTML・SVG等の能動的な内容をアプリと同じ権限で表示しない。確認: ファイルを開いてもアプリのCookie・認証情報に触れられない。
- [ ] **42 P0 帳票と一括出力** — 出力専用の権限と対象範囲を定め、生成ファイルにも有効期限・取得時の認可を付ける。確認: 画面の絞り込みを変えても許可範囲を越えず、出力理由・件数・操作者を追える。
- [ ] **43 P0 CSVの数式対策** — 氏名・メモ等が表計算ソフトで数式として実行されないよう、対象ソフトに合う出力方法を選ぶ。確認: `=`等から始まる値を試し、保存・再オープン後も安全。引用符だけを付けて完了にしない。[OWASP CSV Injection](https://community.owasp.org/attacks/CSV_Injection)
- [ ] **44 P0 通知の漏えい防止** — メール・プッシュの本文を必要最小限にし、鍵情報・事故の詳細等は認証後の画面で確認させる。確認: 他社・退職者への送信、CCの混入、ロック画面への機密表示がなく、リンク先も認可される。

### 操作記録と不正変更の防止

障害調査用ログに加え、誰がどの業務情報へアクセス・変更したかを追える監査記録を持つ。ログ自体へのアクセスと、秘密・個人情報の記録範囲も制限する。[OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

- [ ] **45 P0 監査する操作** — ログイン、認可拒否、権限変更、機密情報の閲覧、一括出力、勤怠修正・承認、削除、保守アクセスを記録する。確認: 会社・操作者・対象ID・操作・結果・時刻・リクエストIDで追跡できる。
- [ ] **46 P0 勤怠と申請の履歴** — 元の打刻、修正理由、変更者、承認者を残す。承認・確定後の再編集は専用の手順にする。確認: 警備員が承認済みに偽装できず、元の記録と変更経緯を確認できる。
- [ ] **47 P0 重複と競合** — 打刻・申請・承認は再送による二重処理を防ぎ、同時更新にはDB制約・トランザクション・更新競合の検出を使う。確認: 連打や通信再試行で二重打刻・二重承認・意図しない上書きが起きない。
- [ ] **48 P0 ログの機密性** — パスワード・Cookie・トークン・本文・機密クエリを記録しない。監査の変更情報は許可項目に絞り、ログの閲覧権限を分ける。確認: API・プロキシ・監視サービス・ブラウザのエラー送信を含め、秘密が残らない。
- [ ] **49 P1 記録の保全** — 時刻同期、保存期間、容量管理、改ざんしにくい保管を設定する。確認: 通常の業務利用者や侵害されたAPI権限で過去の監査記録を消せず、記録停止を検知できる。

### バックアップと障害と事故対応

勤務の確認や現場連絡が止まる場合に備え、復旧手順と業務を継続する手順を両方持つ。個人データの漏えい等では、内容に応じて委員会への報告・本人通知が必要となるため、責任分担と判断手順を先に決める。[個人情報保護委員会の漏えい等対応](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)

- [ ] **50 P0 バックアップと復元** — DBと必要な添付を自動バックアップし、暗号化・アクセス制限・別管理の保存を行う。確認: 新しい環境へ実際に復元し、業務データ・添付・会社境界の整合性を確認する。
- [ ] **51 P0 復旧の目標** — 許容するデータ損失時間と復旧時間を決める。障害中の連絡・出退勤記録・復旧後の照合方法も用意する。確認: 担当者が手順を実行でき、復元に必要な鍵も取り出せる。
- [ ] **52 P0 監視と対応先** — ログイン失敗急増、認可拒否、大量出力、DB障害、バックアップ失敗、容量逼迫を監視する。確認: 通知先・担当・初動手順が決まり、テスト通知が届く。
- [ ] **53 P0 情報漏えいへの初動** — 利用停止、セッション・秘密の失効、証拠保全、影響調査、利用会社への連絡を手順化する。委員会への報告・本人通知の対象と期限、委託時の役割も確認する。確認: 運営者と利用会社の連絡窓口・責任分担がある。
- [ ] **54 P1 端末と利用者教育** — スマートフォン・共用PCの画面ロック、更新、紛失時の連絡、ログアウトを定める。個人のチャット・写真フォルダーへの機密コピーを避け、フィッシング対策を共有する。確認: 紛失報告から該当端末のアクセスを停止できる。
- [ ] **55 P1 契約と外部委託** — クラウド・メール・監視の保存地域、再委託、アクセス、事故連絡、契約終了時の返却・削除を確認する。確認: 委託・国外での取扱いに必要な説明・監督等を整理し、会社ごとの復元や削除が他社へ影響しない。

### 開発とリリースと継続改善

公開前の確認範囲を決め、機能追加のたびに認証・認可・会社境界を検証する。検証要件の整理にはOWASP ASVSを使い、採用する版と要件を記録する。[OWASP ASVS](https://owasp.org/projects/asvs)

- [ ] **56 P0 依存関係と更新** — `npm.cmd run security:audit`を維持し、Node.js・PostgreSQL・コンテナも更新対象にする。確認: 指摘の影響を評価して修正し、未対応にする場合は理由・期限・担当を記録する。
- [ ] **57 P0 リポジトリとCI** — レビュー・ブランチ保護・管理者MFAを設定し、CIの権限と秘密を限定する。既存のActionsのSHA固定を維持する。確認: 外部PR等の未信頼コードへ本番秘密やデプロイ権限が渡らない。
- [ ] **58 P0 業務のセキュリティテスト** — 基盤のテストに加え、会社・拠点・本人・役割・失効・ファイル・出力を検証する自動テストを追加する。確認: 正しい操作の成功と、不正な操作の拒否を実際のAPI・DB経路で再現できる。
- [ ] **59 P1 第三者の診断** — 本番公開前や認証・添付・外部連携の大きな変更時に、担当者以外のレビューや脆弱性診断を行う。確認: 対象・結果・修正・再確認を残し、重大な未修正がある機能は公開しない。
- [ ] **60 P2 定期的な見直し** — 権限、復元、インシデント訓練、外部委託、脅威と費用を見直す。必要に応じWAF・DDoS対策・追加監視を強化する。確認: 見直し日と担当が決まり、基本対策を置き換えるものとして扱わない。

## 最初に取り組む順序

| 順序 | 作業 | 完了の目安 |
| --- | --- | --- |
| 1 | 保存するデータと役割・所属範囲を決める | 不要な個人情報を除き、誰が何を扱えるか説明できる |
| 2 | 会社・拠点・利用者のモデルと認証を作る | 本人確認、所属確認、管理者MFA、利用停止が動く |
| 3 | 最初の業務テーブルとAPIへ認可・会社境界を適用する | 一覧・詳細・更新を含め他社・無権限のアクセスを拒否する |
| 4 | 拒否する操作のテストと監査記録を追加する | IDの変更、権限の偽装、失効後のアクセスを検出・拒否する |
| 5 | HTTPS配信・秘密管理・監視・バックアップを整える | 公開範囲が確認でき、復元と事故対応の手順を実行できる |
| 6 | 対象機能のP0を確認して実データの利用を始める | 担当者・確認日・証跡が揃い、機能追加にも同じ基準を使う |

## 公開前に確認する具体例

以下は今後実施する検証例であり、現在のモックで合格した結果ではない。架空データのA社・B社と、権限の異なる利用者を用意する。APIが拒否しても副作用が起きていないことをDB・ファイル・通知で確認する。

| 試す操作 | 期待する結果 |
| --- | --- |
| 未ログインで隊員APIや添付URLを直接開く | 個人情報が返らず、業務データも変更されない |
| A社の利用者がURL・本文・ヘッダーをB社のIDへ変更する | 一覧・件数・詳細・更新・出力の全経路で他社にアクセスできない |
| A社の配置にB社の隊員を登録する | API・DBで関連付けが拒否される |
| 警備員が別隊員や担当外現場のIDへ変更する | 同じ会社でも許可された範囲を超えて閲覧・更新できない |
| 閲覧者が更新APIを直接呼ぶ、本人が`role`を送る | 更新と権限昇格が拒否される |
| ログイン中に退職・停止・権限縮小し、古いCookie等を再利用する | 旧権限が使えず、署名付きURL等の失効方針も満たす |
| A社・B社の処理を同じDB接続・キャッシュで続ける | 前の会社の情報が次の処理へ残らない |
| 日報へスクリプト、検索へSQL、CSVへ数式を含む値を入れる | コードとして実行されず、対象ソフトでの再表示も安全 |
| 偽装ファイル・巨大本文・連続ログイン・偽装転送ヘッダーを送る | 検証・容量・頻度の制限が有効で、業務を過剰に圧迫しない |
| 退職者宛の通知、他社の添付URL、生成済み帳票を取得する | 送信前・取得時の会社と利用権限が守られる |
| 打刻・承認を連打・再送し、同じ記録を同時更新する | 二重処理や履歴を失う上書きがなく、競合を適切に扱う |
| 新しい環境へバックアップを復元する | 必要なDB・添付・鍵が揃い、会社の分離と復旧時間を確認できる |

既存の`npm.cmd run check`は型チェック・Lint・バックエンドテスト・ビルド、`npm.cmd run security:audit`は依存パッケージ監査。現時点で業務認可・会社分離の自動テストは含まれない。画面の表示確認やパッケージ監査だけで、業務データを安全に扱えると判断しない。

各項目の記録には、次の列を使う。未対応項目には担当と期限を付け、完了には証跡を残す。

| 項目ID | 状態 | 担当 | 期限 | 確認日 | 証跡または対象外の理由 |
| --- | --- | --- | --- | --- | --- |
| 15 | 未対応 | 未割当 | 未設定 | 未確認 | 会社の確定方法を設計する |

運用周期の初期案は以下。導入会社の体制・契約と扱う情報に合わせて決定する。

| タイミング | 確認内容 |
| --- | --- |
| 入退社・異動・紛失の都度 | 権限の付与・縮小・停止、セッション失効、通知先 |

| 月次 | 利用者・運営者の権限、期限付き保守アクセス、未対応の脆弱性 |
| 四半期と大きな構成変更時 | 復元訓練、事故対応訓練、保存・削除、委託先の変更 |
